Jobs move work out of the request. FrogBot stores each job in your database, and a runner picks it up later. No Redis or separate queue service is needed.

| Use it for | Example |
| --- | --- |
| Slow work a hook shouldn't wait for | Send a welcome email, sync a record to a CRM, create embeddings |
| Work at a later time | Unpublish a post at midnight, remind a trial user after 7 days |
| Recurring work | A nightly report, an hourly sync |
| Steps that must survive failures | Charge a card, email the receipt, then mark the order paid |
| Waiting on a person | Pause until a manager approves, then continue |

## How it fits together

| Piece | What it is | Read |
| --- | --- | --- |
| Task | One function with typed input and output. | [Tasks](/jobs-queue/tasks) |
| Workflow | A function that runs tasks in order and resumes from the step that failed. | [Workflows](/jobs-queue/workflows) |
| Job | One queued run of a task or workflow, stored as a record. | [Queue and run jobs](/jobs-queue/queues) |
| Queue | A name that groups jobs. Runners pick jobs from the queues you choose. The default is `default`. | [Queue and run jobs](/jobs-queue/queues) |
| Schedule | A cron rule that queues a task or workflow. | [Schedules](/jobs-queue/schedules) |
| Runner | What claims and runs jobs: a worker process, `autoRun`, the run URL, or `jobs.run`. | [Job workers](/jobs-queue/workers) |
| Wait | A pause inside a workflow until a reply or a date. | [Durable waits](/jobs-queue/waits) |

Queuing and running are separate steps. A job stays in the database until a runner that covers its queue claims it.

## Quick start

Register a task:

```ts
import { buildConfig } from 'frogbot'

export default buildConfig({
  // ...
  jobs: {
    tasks: [
      {
        slug: 'send-welcome-email',
        retries: 3,
        inputSchema: [{ name: 'userId', type: 'text', required: true }],
        handler: async ({ input, req }) => {
          const user = await req.frogbot.findByID({
            collection: 'users',
            id: input.userId,
            overrideAccess: true,
          })

          await req.frogbot.email.sendEmail({
            to: user.email,
            subject: 'Welcome',
            html: '<p>Welcome aboard.</p>',
          })

          return { output: {} }
        },
      },
    ],
  },
})
```

Queue it from a hook:

```ts
{
  slug: 'users',
  hooks: {
    afterChange: [
      async ({ doc, operation, req }) => {
        if (operation !== 'create') return

        await req.frogbot.jobs.queue({
          task: 'send-welcome-email',
          input: { userId: String(doc.id) },
          overrideAccess: true,
          req,
        })
      },
    ],
  },
}
```

Run it. In production, start a worker beside your web server:

```sh
pnpm exec frogbot jobs:run --all-queues --handle-schedules
```

In development, or on one always-on server, add `autoRun: [{ cron: '* * * * *', allQueues: true }]` to `jobs` instead. On serverless hosts, call the [run URL](/jobs-queue/queues#run-jobs-over-http) from a cron.

## Common mistakes

| Symptom | Cause | Fix |
| --- | --- | --- |
| Jobs are queued but never run | No runner covers their queue. | Run a worker with `--all-queues`, or add the queue to `autoRun`. See [Troubleshooting](/jobs-queue/workers#troubleshooting). |
| A scheduled task never runs | Nothing handles schedules. | Add `--handle-schedules` to a worker, or use `autoRun` or the run URL. See [Schedules](/jobs-queue/schedules). |
| Jobs stop on a serverless host | `autoRun` needs a long-running process. | Call the [run URL](/jobs-queue/queues#run-jobs-over-http) from a cron. |
| A job runs twice | Retries and crash recovery are at least once. | Make external calls idempotent. See [Leases and crash recovery](/jobs-queue/queues#leases-and-crash-recovery). |
| Calls fail with an access error | The default `jobs.access` rules need a signed-in user. | Pass `overrideAccess: true` from trusted server code. |

## Configuration reference

### Jobs options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `tasks` | `TaskConfig[]` (from `frogbot`) | `[]` | Tasks that can be queued or run inside workflows. See [Task options](/jobs-queue/tasks#task-options). The slug `frogbot-sweep-waitpoints` is reserved. |
| `workflows` | `WorkflowConfig[]` | `[]` | Workflows that orchestrate tasks. See [Workflow options](/jobs-queue/workflows#workflow-options). |
| `access` | `{ queue?, run?, cancel? }` | Signed-in users | Access rules checked when a call sets `overrideAccess: false`. See [Access](/jobs-queue/queues#access). |
| `autoRun` | `AutorunCronConfig[] \| (() => AutorunCronConfig[] \| Promise<AutorunCronConfig[]>)` | No runners | In-process cron runners that claim queued jobs. They do not queue new jobs, apart from handling schedules. FrogBot appends its own all-queues runner, once, when agents have schedules or piece triggers or a collection has an AI field. That runner logs job errors but not the "Running N jobs." line, so a quiet app keeps a quiet log; this also hides that line for your own jobs it runs. Avoid on serverless platforms. See [Autorun options](#autorun-options). |
| `shouldAutoRun` | `() => boolean \| Promise<boolean>` | Always run | Checked on each autorun tick before jobs are claimed. Return `false` to skip the tick. See [Disable web autorun](/jobs-queue/workers#disable-web-autorun). |
| `deleteJobOnComplete` | `boolean` | `true` | Delete each job record once it completes successfully. Set `false` to keep completed records. |
| `processingOrder` | `Sort \| { default?: Sort; queues: Record<string, Sort> } \| ((args) => Sort \| Promise<Sort>)` | `'createdAt'` (oldest first) | Order jobs are claimed in, globally, per queue, or computed from the `run` arguments. `'-createdAt'` claims newest first. |
| `jobsCollectionOverrides` | `({ defaultJobsCollection }) => CollectionConfig` | — | Returns a modified jobs collection. Its access functions get `FrogBotRequest`, and `rolesPlugin` binds and checks `allow()` there like on any collection, so `read: allow('admin')` works. `allow()` own clauses aren't accepted on it. FrogBot still adds its `jobId` and `waitpoint` fields, replacing any with those names. |
| `processingLease` | `{ duration?: number; safetyBuffer?: number }` | 20 minutes, 30 seconds | Job lease length and write cutoff. See [Leases and crash recovery](/jobs-queue/queues#leases-and-crash-recovery). |
| `waitpoints` | `{ defaultExpiresIn?: number; maxExpiresIn?: number }` | 7 and 30 days | Resumable-wait lifetimes. See [Expiry](/jobs-queue/waits#expiry). |


### Autorun options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `cron` | `string` | `'* * * * *'` | When the runner ticks. Accepts an optional leading seconds field. |
| `queue` | `string` | `'default'` | Queue to schedule and claim from. |
| `allQueues` | `boolean` | `false` | Schedule and claim from every queue; `queue` is ignored. |
| `limit` | `number` | `10` | Maximum jobs claimed per tick. |
| `disableScheduling` | `boolean` | `false` | Skip enqueueing scheduled jobs on each tick. |
| `silent` | `boolean \| { info?: boolean; error?: boolean }` | `false` | Suppress the job system's info logs, error logs, or both. |

### Database requirements

Use the FrogBot adapters: `@frogbotai/db-postgres`, `@frogbotai/db-vercel-postgres`, `@frogbotai/db-sqlite`, `@frogbotai/db-d1-sqlite`, or `@frogbotai/db-mongodb`. They provide atomic claims and conditional lease updates without Redis.

The jobs collection includes a `jobId` field that is unique while its job is unfinished. New SQL projects get the partial unique index through their generated [database migrations](/database/migrations); apply them before starting workers. MongoDB creates its index on connect. See [SQLite and D1 requirements](/jobs-queue/workers#sqlite-and-d1) for `RETURNING` support and local development.
