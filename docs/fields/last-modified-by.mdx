`lastModifiedByField` returns a [Relationship field](/fields/relationship) that FrogBot sets to the user who last saved the record. It is set on create and on every later save by a user, the same way `updatedAt` changes on every save. People and agents can't write it, and agents and generated types are told that FrogBot sets it. You don't write any hooks or access rules.

```ts
import { createdByField, lastModifiedByField } from 'frogbot'
import type { CollectionConfig } from 'frogbot'

export const Tickets: CollectionConfig = {
  slug: 'tickets',
  fields: [
    { name: 'title', type: 'text', required: true },
    createdByField({ name: 'createdBy' }),
    lastModifiedByField({ name: 'lastModifiedBy' }),
  ],
}
```

The result is a plain single `relationship` field to your user collection. It works at the top level and inside groups, tabs, rows and collapsibles, but not inside arrays or blocks. To record who created a record, use a [Created by field](/fields/created-by).

A last modified by field holds one user that FrogBot sets, so `hasMany`, `minRows`, `maxRows`, `localized`, `defaultValue`, `required`, `access.create` and `access.update` are not accepted, and `relationTo` takes one slug. TypeScript rejects them, and setting any of them from JavaScript fails at startup with an error naming the field:

```text
lastModifiedByField "lastModifiedBy": hasMany is not supported
lastModifiedByField "lastModifiedBy": relationTo must be one collection slug
```

## Who counts as the user

| Where the save comes from | Last modified by |
| --- | --- |
| Admin panel, REST or GraphQL while signed in | The signed-in user |
| An API key, including [MCP](/plugins/mcp) tools | The key's owner |
| A chat agent turn | The person chatting |
| The Local API with a `user` | That user |
| No user: the Local API without `user`, jobs, scheduled agent turns, server scripts | Unchanged. Empty on create. |

Every save by a user counts, including autosaves, drafts, bulk updates and version restores. FrogBot doesn't compare the old and new values, so a save that changes nothing still records the user.

<Warning>
  A save with no user leaves the field unchanged. After a job or scheduled agent turn changes a record, the field still shows the last person who saved it, even though that person didn't make the latest change. If you need to know which saves had no user, the [audit log plugin](/plugins/audit-log) records every save.
</Warning>

## Which user collection

By default the field points at your user collection: the one `admin.user` names, or the only auth collection, or the `users` collection FrogBot adds when you have none. Set `relationTo` to point at another auth collection:

```ts
lastModifiedByField({ name: 'editedByAdmin', relationTo: 'admins' })
```

If the request's user comes from a different auth collection than the field points at, the save counts as having no user, so the field stays unchanged. With the example above, a save by a `users` user leaves `editedByAdmin` as it was, and a save by an `admins` user sets it.

`relationTo` is filled in when the config is built, after plugins have run. With more than one auth collection and no `admin.user`, startup fails. Plugins can add an auth collection: the [MCP plugin](/plugins/mcp) adds one for its keys, so an app using it needs `admin.user` or an explicit `relationTo`.

```text
[frogbot] Last modified by field 'lastModifiedBy' in collection 'tickets': Multiple auth collections found (users, admins). Set `admin.user` to the slug of your user collection.
```

A `relationTo` that isn't an auth collection, and a field inside an array or blocks, also fail at startup:

```text
[frogbot] Last modified by field 'lastModifiedBy' in collection 'tickets' must point at an auth collection; 'posts' is not one.
[frogbot] Last modified by field 'items.lastModifiedBy' in collection 'tickets' can't be inside an array or blocks.
```

## Read-only to people and agents

The admin panel shows the field as read-only. A value sent through the admin panel, REST, GraphQL, MCP, agent tools or a CSV import is dropped without an error, and the rest of the record saves.

## Seeds and migrations

Trusted server code can set the value when it creates a record. This is the Local API with access overridden, which is its default:

```ts
await frogbot.create({
  collection: 'tickets',
  data: { title: 'Imported ticket', lastModifiedBy: ana.id },
})
```

After the record is created, only saves set the value. A value sent with a later update is ignored, including through the Local API.

## Recalculated values

Writes that only recalculate a value for you, rather than record a person's change, don't change the field. A write marks itself this way by setting the `frogbotAIFieldRun` key in the request [context](/hooks/context): any update that carries it keeps the previous last modified by, even when the request has a user.

## Duplicates and versions

- **Duplicate:** the copy doesn't inherit the value. The person duplicating becomes its last modifier.
- **Autosave and drafts:** each save records the user who made it.
- **Restoring a version:** the person restoring becomes the last modifier.

## Existing records

Adding the field to a collection that already has records leaves it empty on those records until a user next saves them.

## Admin options

Last modified by fields support the standard [field admin options](/fields/overview#admin-options), plus the Relationship field's options. `admin.readOnly` is always `true`.

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `allowEdit` | `boolean` | `true` | Shows a button on the selected user that opens it in a drawer, for people who can read the user collection. |
| `allowCreate` | `boolean` | `true` | Has no effect, because the field is read-only. |
| `appearance` | `'select' \| 'drawer'` | `'select'` | Has no effect on the read-only input beyond hiding the dropdown arrow with `'drawer'`. |
| `isSortable` | `boolean` | `true` | Has no effect, because the field holds one user. |
| `sortOptions` | `string` | — | Has no effect, because the field is read-only. |
| `placeholder` | `string \| (({ i18n, t }) => string)` | — | Text shown when the field is empty. |

FrogBot marks the field in `admin.custom.frogbot.kind`. Your own `admin.custom` keys, and other keys under `admin.custom.frogbot`, are kept.

## Display, sorting and filtering

The [List](/admin/overview), [Board](/admin/collection-board) cards and [Calendar](/admin/collection-calendar) events show the user's title, which is the field named by the user collection's `admin.useAsTitle`. Without one, they show the user's ID. Someone who can't read the user collection sees what any relationship they can't read shows. The document view shows the user in a read-only relationship input.

The field sorts and filters like any single relationship, in the admin panel and in REST and Local API queries:

```ts
const editedByBen = await frogbot.find({
  collection: 'tickets',
  where: { lastModifiedBy: { equals: ben.id } },
  sort: '-updatedAt',
})
```

## Stored value

The field stores the user's ID, the same as a [single relationship](/fields/relationship#has-one), and populates it to the user with `depth`. The generated TypeScript type is the same as any single relationship to the user collection, such as `lastModifiedBy?: (number | null) | User`.

## Agents and generated types

A last modified by field describes itself to agents using FrogBot's [MCP tools](/plugins/mcp) and in [generated types](/typescript/generating-types):

```text
Set by FrogBot to the user who last saved the record; read-only
```

With a string `admin.description`, or a translated one with an `en` entry, this text is added after it in parentheses. The admin panel still shows only your description.

```ts
lastModifiedByField({ name: 'lastModifiedBy', admin: { description: 'Who touched the ticket last' } })
```

```text
Who touched the ticket last (set by FrogBot to the user who last saved the record; read-only)
```

A function `admin.description` isn't copied, so the text stands alone. The text is English only. Generated types show it as a comment above the property. To change it, add your own `typescriptSchema` entry, which runs after the field's entry.
