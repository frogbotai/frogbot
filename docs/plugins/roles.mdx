The roles plugin stores code-defined role assignments on users and provides access helpers. It does not add access rules to your collections.

## Install

```bash
pnpm add @frogbotai/plugin-roles
```

## Define roles

```ts
import { rolesPlugin } from '@frogbotai/plugin-roles'
import { buildConfig } from 'frogbot'

export default buildConfig({
  collections: [
    {
      slug: 'users',
      auth: true,
      fields: [],
    },
  ],
  plugins: [
    rolesPlugin({
      roles: [
        'admin',
        'member',
        'finance',
        { slug: 'compliance', label: 'Compliance Officer' },
      ],
    }),
  ],
})
```

When roles are listed, the plugin adds a `roles` multi-select field to the `users` auth collection. Assignments are stored as slugs. There is no role-definition collection.

Roles are literal strings. No slug is reserved, and no role receives implicit access. `admin` is a common convention, but it is not a superuser unless your access functions grant it.

`rolesPlugin()` and `rolesPlugin({ roles: [] })` are inert and add no field.

## Apply access

`allow(...clauses)` composes role, ownership, and function clauses into a FrogBot access function:

```ts
import { allow, hasRole, ownRows } from '@frogbotai/plugin-roles'

const projects = {
  slug: 'projects',
  access: {
    create: allow({ role: 'member', own: 'owner' }),
    read: allow('admin', 'finance', { role: 'member', own: 'owner' }),
    update: allow('admin', { role: 'member', own: 'owner' }),
    delete: allow('admin'),
  },
  fields: [
    {
      name: 'owner',
      type: 'relationship',
      relationTo: 'users',
      required: true,
    },
    {
      name: 'reviewNotes',
      type: 'text',
      access: {
        read: allow('admin', 'compliance'),
        update: allow('compliance'),
      },
    },
  ],
}

const invoices = {
  slug: 'invoices',
  access: {
    read: ({ req }) => hasRole(req, 'admin', 'finance') || ownRows(req, 'user'),
  },
  fields: [],
}
```

Every role must be written where it should apply. For example, `allow('finance')` denies a user assigned only `admin`; use `allow('admin', 'finance')` to grant both.

An ownership clause names a relationship field. On create, FrogBot stamps that field when the matching role grants access. On read, update, and delete, it returns an ownership query. Function clauses returning `false` abstain rather than vetoing another clause.

Ownership and `Where` clauses are for collection access. Boolean role and function clauses also work in field and agent access.

## Request helpers

```ts
import { hasRole, isLoggedIn, ownRows, rolesOf, viaApiKey } from '@frogbotai/plugin-roles'

isLoggedIn(req)
hasRole(req, 'finance', 'auditor')
rolesOf(req)
ownRows(req, 'owner')
viaApiKey(req)
```

| Helper | Result |
| --- | --- |
| `isLoggedIn(req)` | Whether `req.user` exists. |
| `hasRole(req, ...roles)` | Whether the user has any supplied literal role. |
| `rolesOf(req)` | Effective role slugs for the request. |
| `ownRows(req, field)` | An ownership query, or `false` without a user. |
| `viaApiKey(req)` | Whether authentication used the API-key strategy. |

## Role field access

The injected `roles` field uses FrogBot's default field access. Use `rolesFieldAccess` when role assignments need different access rules:

```ts
rolesPlugin({
  roles: ['owner', 'member'],
  rolesFieldAccess: {
    read: ({ req }) => req.user?.id === req.data?.id,
    update: ({ req }) => hasRole(req, 'owner'),
  },
})
```

The object is passed directly to the injected field.

## Default role

By default, new users receive no role. Set `defaultRole` to configure the injected field's `defaultValue`:

```ts
rolesPlugin({
  roles: ['admin', 'member'],
  defaultRole: 'member',
})
```

The default must be listed in `roles`. Explicit assignments, including `roles: []`, are preserved. Existing users are unchanged.

## Custom role sources

By default, helpers read `req.user.roles`. Use `resolveRoles` when assignments come from another synchronous source, such as JWT claims or tenant membership:

```ts
rolesPlugin({
  roles: ['admin', 'member'],
  resolveRoles: (req) => req.user?.tenantRoles ?? [],
})
```

The resolver must return listed slugs. Its result is cached once per request and shared by predicates and `allow()` clauses.

## Bootstrap access

The plugin does not promote the first user. Bootstrap privileged assignments explicitly with FrogBot's Local API from a seed or migration, which bypasses access control by default:

```ts
await frogbot.update({
  collection: 'users',
  id: ownerUserId,
  data: { roles: ['admin'] },
})
```

You can also assign roles when seeding users:

```ts
await frogbot.create({
  collection: 'users',
  data: { email, password, roles: ['admin'] },
})
```

For application-managed onboarding, add a userland collection hook that derives the assignment from your own invite, tenant, or deployment rules. Keep that bootstrap condition in application code and remove or disable one-time logic after it succeeds.
