The Dojo plugin adds the `dojo` target to [`frogbot deploy`](/deployment/overview) and `frogbot dojo`, which manages Dojo from the terminal, and runs your app on Dojo with no setup: uploads go to the app's own storage, and AI goes through Dojo's gateway. Apps made with `create-frogbot-app` already list it.

## Install

```bash
pnpm add @frogbotai/plugin-dojo
```

```ts
import { dojo } from '@frogbotai/plugin-dojo'
import { buildConfig } from 'frogbot'

export default buildConfig({
  // ...
  plugins: [dojo()],
})
```

## Options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `signIn` | `boolean` | `true` | Adds [Sign in with Dojo](#sign-in-with-dojo) on Dojo. Set `false` to leave the app's sign-in methods alone. |

## Commands

`dojo()` adds `frogbot dojo`, which does everything a person can do in Dojo from the terminal, for people and coding agents, and `frogbot share`, which is `frogbot dojo apps share` with the same flags. In an app that lists `dojo()`, run them as [plugin commands](/getting-started/cli#plugin-commands). The package also installs its own bin, so the same commands run without an app, or in an app that doesn't list `dojo()`:

```bash
npx frogbot share
npx @frogbotai/plugin-dojo apps pull deals
```

`frogbot deploy` with no target runs the same deploy as `apps share`, because `dojo()` registers `dojo` as a [deploy target](/getting-started/cli#plugin-deploy-targets).

| Command | Arguments | Description |
| --- | --- | --- |
| `login` | — | Signs in with a code you confirm in the browser. The first sign-in makes your Dojo account. |
| `logout` | — | Revokes the stored sign-in and removes it from `auth.json`. See [`dojo logout`](/getting-started/cli#dojo-logout). |
| `whoami` | — | Shows the account, the Dojo URL and your workspaces. |
| `workspaces list` | — | Lists the workspaces you're in. |
| `workspaces create` | `<name>` | Creates a workspace you own. |
| `workspaces rename` | `<slug> <name>` | Renames a workspace you own. |
| `members list` | `--workspace` | Lists a workspace's members and roles. |
| `members add` | `<email>`, `--role owner\|member`, `--workspace` | Adds someone by email; they join when they sign in with it. |
| `members role` | `<email> <role>`, `--workspace` | Changes a member's role. |
| `members remove` | `<email>`, `--workspace`, `--yes` | Removes a member, or yourself. |
| `apps share` | `--data`, `--no-data`, `--workspace`, `--name`, `--no-keys`, `--skip-key`, `--yes`, `--update-keys` | Uploads the app in this folder to Dojo, builds it and prints its live URL. See [`dojo apps share`](/getting-started/cli#dojo-apps-share). |
| `apps pull` | `<app>` | Downloads an app you own or edit into a new folder. See [`dojo apps pull`](/getting-started/cli#dojo-apps-pull). |
| `apps logs` | `<app>`, `--follow` | Prints an app's recent logs, or follows them. See [`dojo apps logs`](/getting-started/cli#dojo-apps-logs). |
| `apps list` | `--workspace` | Lists every app you can see. |
| `apps get` | `<app>` | Shows an app's address, whether it has started, and your access. |
| `apps create` | `<name>`, `--workspace` | Creates an empty app to share to later. A name whose slug would be digits alone is refused, since digits name an app by id. |
| `apps rename` | `<app> <name>` | Renames an app; its address stays. |
| `apps delete` | `<app>`, `--yes` | Deletes an app and everything in it. |
| `deployments list` | `<app>` | Lists an app's deployments, newest first. |
| `deployments logs` | `<id>`, `--follow` | Prints the end of a deployment's build log, or follows it until the build ends. |
| `env list` | `<app>` | Lists an app's environment keys, masked. |
| `env set` | `<app> KEY=value…` | Sets keys; the app restarts once. |
| `env unset` | `<app> KEY…`, `--yes` | Removes keys; the app restarts once. |
| `domains get` | `<app>` | Shows the custom domain, the CNAME record to add, and its certificate status. |
| `domains set` | `<app> <host>`, `--yes` | Points a domain you own at the app. Asks before replacing a domain it already has. |
| `domains clear` | `<app>`, `--yes` | Removes the custom domain. |
| `sharing list` | `<app>` | Lists who an app is shared with, and at which level. |
| `sharing invite` | `<app> <email>…`, `--level use\|editor\|owner` | Shares the app; Dojo emails each person. |
| `sharing leave` | `<app>`, `--yes` | Removes you from an app shared with you. |
| `keys list` | — | Lists your Dojo API keys, with the key that made each one. |
| `keys create` | `<name>`, `--can-mint` | Creates a key and prints it once. |
| `keys revoke` | `<id>`, `--yes` | Revokes a key. |
| `billing status` | `--workspace` | Shows a workspace's plan, status and paid apps. |
| `billing manage` | `--workspace` | Prints the link to change the card, see invoices or cancel. |

`<app>` is the app's slug, such as `deals` for `deals.frogbot.app`, or its id. Digits that are one app's id and another app's slug are refused; name that app by its id. Lists read every page. `frogbot dojo --help`, `frogbot dojo apps --help` and `frogbot dojo apps share --help` list the commands, a noun's verbs and a verb's flags. An unknown command or verb prints the list and exits with code `2`.

### Scripts and agents

- **`--json`** on any command prints one JSON value on stdout and nothing else. Sign-in links, progress and build lines go to stderr, and a failed command prints nothing on stdout. `apps share` (and `frogbot share`) prints the same `{ target, ok, dryRun, issues, result }` object as [`frogbot deploy --json`](/deployment/overview), even when it fails. `apps logs --follow` never ends, so it refuses `--json`.
- **`FROGBOT_DOJO_TOKEN`** is a Dojo API key every command uses, ahead of the stored sign-in. When Dojo refuses it, the command exits with code `1` instead of starting a browser sign-in. `FROGBOT_DOJO_URL` targets another Dojo. Sharing never uploads either one from `.env` as an app key.
- **No terminal.** Every question has a flag, or fails naming it. `apps delete`, `members remove`, `keys revoke`, `sharing leave`, `env unset`, `domains clear`, and `domains set` when it replaces a domain, ask before acting, and need `--yes` without a terminal. `apps delete` looks the app up first and names it in the question.
- **Refusals.** A `402` prints Dojo's upgrade link. A `403` says which access the command needs, such as owner access to the app.
- **Creating keys.** `keys create` mints a key with the CLI's sign-in, using the API keys plugin's [keys that mint keys](/plugins/api-keys#keys-that-mint-keys): the new key is never broader than the sign-in, and `keys list` shows which key made it. When Dojo doesn't let the sign-in create keys, the command prints the link to create one in the browser and exits with code `1`.
- **People stay in the loop for two things.** Signing up and confirming a sign-in happen in the browser, through `login`, and so does paying: `billing manage` prints the link.

## On Dojo

Dojo adds this plugin itself when it builds an app, after the app's own plugins, so an app runs there without listing it. An app that lists `dojo()` gets it once, not twice. A listed `dojo()` also runs after every other plugin, wherever it is in `plugins`, so it sees the upload collections and AI providers they add.

Outside Dojo, `dojo()` only adds the `dojo` and `share` commands and the `dojo` deploy target, and lists the badge and the sign-in buttons for the import map. On Dojo, where `DOJO=1`, it also changes:

- **Storage.** When the app sets no `storage`, every upload collection is stored in the app's bucket under its slug. Files stay private and are served through the app, so its access rules apply.
- **AI.** When every provider in `ai.providers` is a built-in one with no key, they are replaced by one `dojo` provider that calls Dojo's gateway. Model IDs such as `openai/gpt-5.4-mini` keep working. Chat, embeddings and images work through the gateway; transcription, speech and video need your own key. An app with no `ai` block, or with any provider key of its own, is left unchanged.
- **Jobs.** Dojo wakes the app to run due jobs. Everyone else gets the app's own `jobs.access.run`.
- **Sign-in.** The login page gets "Continue with Dojo". See [Sign in with Dojo](#sign-in-with-dojo).
- **Badge.** Every FrogBot page gets a small "Made with FrogBot · Share your own" link in the bottom-left corner. Visitors can close it for the rest of their browser session.

### Sign in with Dojo

On Dojo, the plugin adds a `dojo` method, labelled "Dojo", to the user collection's [`auth.signIn`](/authentication/sign-in), after the app's own methods. The user collection is the app's only auth collection, or the one `admin.user` names. Dojo people then sign in with their Dojo account, the way "Continue with Google" works:

- The first time someone signs in to an app, Dojo asks them once to share their name and email address with it. After that it's one click.
- Someone whose email already has an account signs in as that user.
- A new email gets an account only when the collection's [`access.create`](/authentication/sign-in#who-can-sign-up) allows it, so by default the button serves people who already have an account. Open sign-ups with `access: { create: () => true }`.
- While the collection has no users, the [first person](/authentication/sign-in#who-can-sign-up) to sign in gets an account, as with the create-first-user screen.

Turn it off with one line:

```ts
plugins: [dojo({ signIn: false })]
```

Dojo gives each app its own OAuth client, in `DOJO_OAUTH_CLIENT_ID`, `DOJO_OAUTH_CLIENT_SECRET` and `DOJO_URL`. Sign-in never stops the app from starting: when one of them is missing, or the collection can't take a sign-in method (see [Collection requirements](/authentication/sign-in#collection-requirements)), the plugin adds nothing and logs why at start, for example `[plugin-dojo] Sign in with Dojo is off for 'users': DOJO_URL is not set.` The same happens when the collection already has a method with the slug `dojo`.

An app with `sqliteAdapter({ transactionOptions: false })` fails to start once the method is added, because sign-in needs transactions. Remove that option, or use `dojo({ signIn: false })`.
