The API keys plugin adds an `api-keys` collection, API-key authentication, and admin controls for creating and revoking keys. Each user can own multiple named keys, and each key can be revoked independently.

## Install

```bash
pnpm add @frogbotai/plugin-api-keys
```

## Configure

Add the plugin to your FrogBot config. By default, it associates keys with the auth-enabled `users` collection.

```ts
import { apiKeysPlugin } from '@frogbotai/plugin-api-keys'
import { buildConfig } from 'frogbot'

export default buildConfig({
  collections: [
    {
      slug: 'users',
      auth: true,
      fields: [],
    },
  ],
  plugins: [apiKeysPlugin()],
})
```

`frogbot dev` generates the admin import map before starting, so the API Keys collection and its key-creation controls appear on the first load. Click **Create API key** in the API Keys list toolbar, where Create New sits on other collections, to create a named key, and copy the token when it is displayed. The plaintext token cannot be retrieved again.

Build and start-only workflows must run `frogbot generate:importmap` after adding the plugin. The blank template does this automatically during `prebuild`; add the same step to custom CI workflows that invoke `next build` directly. If the server console reports a component missing from the import map, run `frogbot generate:importmap` and rebuild, or restart `frogbot dev`.

## Authenticate requests

Send the key as a Bearer token or through the `X-API-Key` header:

```http
Authorization: Bearer fb_...
```

```http
X-API-Key: fb_...
```

The request authenticates as the user who owns the key. Revoked, [expired](#expiring-keys), malformed, and unknown keys do not authenticate. A Bearer key takes precedence; when the `Authorization` header holds something other than an API key, such as a session token, FrogBot reads the key from the key headers instead. The auth collection's `/me` endpoint returns the key owner and never echoes the key back.

A request records its time in the key's **Last Used At** about once a minute, so it can lag by up to a minute. Parallel requests that all find it more than a minute old can each record it. Recording it never fails the request: when the write fails, for example on a write conflict between parallel requests, the request still authenticates and the first failure is logged.

When AI is configured, usage rows include an optional `apiKey` relationship identifying the key that authenticated the request. Cookie-authenticated requests omit it, and the relationship follows a custom `collectionSlug`. A key's **Total Cost (USD)** field sums its usage rows, so when [usage retention](/plugins/usage-reports#retention) is on, it covers only the rows still kept.

On a key-authenticated request, `req.user` is the owner with `apiKeyId` and `apiKey`, the key document without its hash, so hooks and access functions can read fields other plugins add to keys. Other plugins find the keys collection through `plugins['plugin-api-keys'].options.collectionSlug` ([Order, slug, and options](/plugins/build-your-own#order-slug-and-options)).

## Configuration options

```ts
apiKeysPlugin({
  authCollection: 'accounts',
  collectionSlug: 'credentials',
  tokenPrefix: 'acme',
  headerNames: ['x-service-key'],
  collection: {
    admin: { group: 'Security' },
    fields: [{ name: 'environment', type: 'text' }],
  },
})
```

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `authCollection` | `string` | `'users'` | Auth-enabled collection whose users own the keys. The plugin throws at startup if the collection is missing or doesn't have auth enabled. |
| `collectionSlug` | `string` | `'api-keys'` | Slug for the generated API-key collection. |
| `tokenPrefix` | `string` | `'fb'` | Prefix placed before generated key values, joined with `_`. Only tokens with this prefix authenticate. |
| `headerNames` | `string[]` | `['x-api-key']` | Request headers checked for a key when `Authorization` doesn't carry one. Replaces the default list. |
| `collection` | `Partial<CollectionConfig>` | — | Collection overrides, including fields, access, hooks, endpoints, and admin configuration. |
| `canRevokeAnyKey` | `(req: FrogBotRequest) => boolean \| Promise<boolean>` | — | Predicate allowing a request to revoke or rotate a key it does not own. Without it, callers revoke and rotate only their own keys. It widens only a signed-in session's reach. A request made with a key still reaches only that key and the keys it minted. |

Collection overrides merge with the generated configuration and changes made by other plugins. The collection uses the `key-round` icon in the admin sidebar; set `collection.admin.icon` to use a different one. The admin controls use the default admin components, and the token dialog ships a small stylesheet built on the admin theme variables.

## Expiring keys

A key works until it is revoked, unless it is given an expiry when it is minted. Post `expiresAt`, an ISO 8601 date in the future, beside `name`. Send a day, such as `2027-02-07`, which means midnight UTC, or a date and time that ends in `Z` or an offset:

```ts
await fetch('/api/api-keys/mint', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ name: 'CI', expiresAt: '2027-02-07T00:00:00.000Z' }),
})
```

`mintApiKey({ req, collectionSlug, tokenPrefix, name, expiresAt })` takes the same option on the server. Both answer `400` for any other format, a day that doesn't exist such as `2027-02-30`, or a date that isn't in the future, and return `expiresAt` with the new key, `null` when it never expires.

- Once `expiresAt` passes, the key no longer authenticates, and its **Last Used At** time stops changing. It stays in the list, with its date in the **Expires** column. Requests made with it get a `401` that says so: see [Revoked and expired keys](#revoked-and-expired-keys).
- `expiresAt` is set only when the key is minted. Nobody can change it afterwards, and `data` can't set it.
- Rotating keeps the old key's `expiresAt`. Rotating a key that has already expired answers `400`, `This key has expired. Mint a new key instead.`, and leaves the old key as it was.
- A key minted by a key expires no later than its parent. A later date, or none, becomes the parent's date; an earlier one is kept.
- The create dialog has an **Expires** day picker, empty by default, with **30 days**, **90 days**, **1 year** and **No expiry** buttons. The key works through the chosen day: the dialog posts the start of the next day in the browser's time zone.

## Revoked and expired keys

A request whose only credential is a revoked or expired key gets a `401` that names the reason, so an agent mints a new key instead of retrying or debugging access rules. The same text is the error message and the `WWW-Authenticate` challenge, on REST, the plugin's endpoints and [MCP](/plugins/mcp):

```http
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer error="invalid_token", error_description="API key expired at 2026-11-01T00:00:00.000Z. Mint a new one with POST /api/api-keys/mint."

{ "errors": [{ "message": "API key expired at 2026-11-01T00:00:00.000Z. Mint a new one with POST /api/api-keys/mint." }] }
```

A revoked key reads `API key was revoked at <date>.` instead. On GraphQL the reason is the error's message. This applies even to collections anyone can read, so the request doesn't quietly return only the public data. Saying so leaks nothing, because the caller already holds the key. An unknown key still gets the usual response, a request that also carries a valid session signs in as that session's user, and a password login with a stale key header still signs in. The plugin's own endpoints keep their `{ "error": "..." }` body.

## Budgets and limits

The plugin has no budgets, rate limits, or model limits of its own. A key authenticates as its owner, so requests made with it pass the owner's [`ai.access`](/ai/overview#control-access) rules. With the [AI policy plugin](/plugins/ai-policy), they use the owner's models and monthly budget, their spend counts toward the owner's total, and each key gets its own model list and monthly cap inside the owner's ([API key limits](/plugins/ai-policy#api-key-limits)).

### Fields from other plugins

Other plugins can add fields to the keys collection, and the plugin keeps them:

- `mint` accepts `data`, fields the plugin didn't define, and passes them to `create`, so their validation runs. The create dialog posts `{ name, data }` and shows validation errors.
- `rotate` copies every field the plugin didn't define from the old key, and runs the create with `req.context.apiKeyRotatedFrom` set to the old key's ID.
- A key minted by a key takes its parent's value for each of these fields; a value posted in `data` is replaced. A request made with a key can't change them on any key: it gets a `403`, `API key "<name>" can't change "<field>" on a key. Sign in to change it.` A plugin that bounds its own field, as the [AI policy plugin](/plugins/ai-policy#api-key-limits) does with models and caps, sets `custom: { 'plugin-api-keys': { inherit: false } }` on it.
- The create dialog renders server components registered under the keys collection's `admin.custom['plugin-api-keys'].createFields` in a collapsed **Limits** section. They read and set the posted `data` with `useCreateKeyData()` from `@frogbotai/plugin-api-keys/client`. With none registered, the dialog has no Limits section.

## Role-aware access

The plugin does not require a role system. By default, callers read and update only the keys they own, and revoke and rotate are limited to the caller's own keys.

A request made with a key reaches only that key and the keys it minted, whatever the access rules or `canRevokeAnyKey` allow. Revoking, rotating or counting any other key answers `404` with `{ "error": "A key can revoke or rotate only itself and the keys it minted. Sign in to manage this key.", "code": "not_found" }`.

To layer roles on top, install [`@frogbotai/plugin-roles`](/plugins/roles) and pass role clauses as the collection access:

```ts
import { apiKeysPlugin } from '@frogbotai/plugin-api-keys'
import { allow, hasRole, rolesPlugin } from '@frogbotai/plugin-roles'

plugins: [
  apiKeysPlugin({
    canRevokeAnyKey: (req) => hasRole(req, 'admin', 'support'),
    collection: {
      access: {
        read: allow('auditor', 'support', { role: 'member', own: 'owner' }),
        update: allow('support', { role: 'member', own: 'owner' }),
      },
    },
  }),
  rolesPlugin({ roles: ['admin', 'member', 'auditor', 'support'] }),
]
```

`canRevokeAnyKey` here lets an admin or support user revoke and rotate other users' keys. It widens only a signed-in session's reach. A request made with a key still reaches only that key and the keys it minted.

`rolesPlugin()` with no roles listed is inert and binds nothing, so `allow()` clauses passed to any plugin deny every request until you list the roles.

## Security behavior

- Plaintext keys are returned only when created.
- The collection stores a SHA-256 hash and a short display prefix, not the plaintext key.
- Collection reads are scoped to the authenticated owner by default.
- Keys are revoked individually without affecting the owning user's other authentication methods.
- Deleting a user also deletes every key that user owns.
- Collection reads and writes, revoke, and rotate are owner-scoped until you widen them.
- Minting and rotating need a signed-in session, or a key with `canMint`. A request authenticated by any other key gets `403`, so a leaked key can't create keys that outlive revoking it. Every key has `canMint` off unless whoever minted it set it. A key can still list and rename its owner's keys, and revoke itself and the keys it minted.

## Keys that mint keys

A session can mint a key with `canMint`, by posting `{ name, data: { canMint: true } }` to `mint`. Requests made with that key can then mint and rotate keys, for a CLI or agent that sets up its own automation without a browser. A key minted by a key is never broader than its parent:

- It records the parent as `mintedBy`, shown in the keys list. Keys a session mints leave it empty.
- It can have `canMint` only because its parent has it.
- It has its parent's values for [fields from other plugins](#fields-from-other-plugins), such as a tenant or environment.
- It [expires](#expiring-keys) no later than its parent.
- A key rotates, revokes and counts with `minted-count` only itself and the keys it minted. Any other key answers `404` and nothing changes. A signed-in session reaches every key its owner has.
- With the [AI policy plugin](/plugins/ai-policy#api-key-limits), its model list and monthly cap stay inside the parent's as well as the owner's. A list or cap it leaves empty is the parent's. Its spend also counts against the parent's cap, so a parent capped at $10 and every key below it together spend at most $10 a month.

Revoking a key revokes every key it minted, and every key those minted, all the way down. To revoke only that key and leave the keys it made working, post `{ "cascade": false }` to `revoke`, or pass `cascade: false` to `revokeApiKey`. An empty body, or one without `cascade`, revokes the whole tree; a body that isn't JSON, or a `cascade` other than `true` or `false`, `null` included, answers `400`. A later revoke of a key further up still reaches the keys that a `cascade: false` revoke left working, and stamps them with the time of that revoke. `GET /:id/minted-count` answers `{ "count": n }`, the number of working keys a cascading revoke would also revoke.

```ts
await revokeApiKey({ req, collectionSlug: 'api-keys', id }); // the key and every key below it
await revokeApiKey({ req, collectionSlug: 'api-keys', id, cascade: false }); // only the key
```

When a cascading revoke would take working keys, including ones below a key revoked on its own, the admin's revoke dialog shows **Also revoke the keys it made**, checked by default. `frogbot dojo logout` revokes only the CLI's own key, so the keys it made keep working.

Rotating mints the new key first and revokes the old one only once the new one exists, so a refused rotation (a cap above the parent's, say) leaves the old key working. The new key keeps the old key's `mintedBy`, including when a key rotates itself, and the keys the old one minted move to the new one.
