Agents wrap AI SDK v7 `ToolLoopAgent` with FrogBot model resolution, request context, access, and hooks. Register code-defined `AgentConfig` objects in the root configuration.

---

## Define one

Provide a URL-safe `slug`, a provider-prefixed model ID or router alias, and instructions.

```ts
import { isStepCount } from 'frogbot'
import type { AgentConfig } from 'frogbot'

export const supportAgent: AgentConfig = {
  slug: 'support',
  model: 'fast',
  instructions: 'Answer support questions and use tools when needed.',
  stopWhen: isStepCount(8),
  access: ({ req }) => Boolean(req.user)
}
```

```ts
type AgentConfig = {
  slug: string
  model: ModelId
  instructions: string
  tools?: readonly AnyTool[]
  inheritTools?: false
  stopWhen?: StopCondition<ToolSet> | StopCondition<ToolSet>[]
  access?: AgentAccess
  triggers?: readonly AgentScheduleTrigger[]
}
```

`stopWhen` defaults to the AI SDK's `isStepCount(20)`. If provided as an array, `stopWhen` must be non-empty.

## Add tools

Agents accept FrogBot `Tool` objects, not raw AI SDK tools. FrogBot converts them internally and supplies request, runtime, slug, and run ID context to every execution.

To connect tools discovered from an external server, use the [MCP server tools recipe](/configuration/mcp).

```ts
import type { Tool } from 'frogbot'
import { z } from 'zod'

const lookupInput = z.object({
  ticket: z.string()
})

export const lookupTicket: Tool<
  typeof lookupInput,
  { ticket: string; status: string }
> = {
  slug: 'lookup-ticket',
  description: 'Look up the current status of a support ticket',
  inputSchema: lookupInput,
  execute: async ({ ticket }, ctx) => {
    ctx.frogbot.logger.info({ ticket }, 'Looking up ticket')

    return {
      ticket,
      status: 'open'
    }
  }
}
```

The execution context has this exact shape.

```ts
type ToolCtx = {
  req: FrogbotRequest
  frogbot: Frogbot
  agent: {
    slug: string
    runId: string
  }
}
```

Attach tools directly to the worker.

```ts
export const supportAgent: AgentConfig = {
  slug: 'support',
  model: 'fast',
  instructions: 'Use lookup-ticket before reporting ticket status.',
  tools: [lookupTicket]
}
```

Inference runs through the embedded gateway. Each model step can request tools, FrogBot executes them with `ToolCtx`, and the loop continues until a stop condition matches.

## Share tools across agents

Add tools to the root configuration to attach them to every agent.

```ts
export default buildConfig({
  tools: [lookupTicket],
  agents: [supportAgent, reportingAgent]
})
```

Toolkits can be spread into the same array, such as `tools: [...todoTools]`. If an agent declares a tool with the same slug, its tool replaces the root tool and FrogBot logs a warning during initialization.

Set `inheritTools: false` when an agent should only use its own tools.

```ts
export const reportingAgent: AgentConfig = {
  slug: 'reporting',
  model: 'fast',
  instructions: 'Create reports from approved data sources.',
  inheritTools: false,
  tools: [queryWarehouse]
}
```

Root tools with `pieceService` use the same validation as agent tools. The matching piece must be registered in the root `pieces` array.

## Organize files

Use folders for organization, then import every config explicitly. FrogBot v0 does not scan a directory or load `AGENT.md` files.

```text
src/
├── agents/
│   ├── index.ts
│   └── support.ts
└── tools/
    └── lookup-ticket.ts
frogbot.config.ts
```

```ts
// src/agents/index.ts
import { supportAgent } from './support'

export const agents = [supportAgent]
```

```ts
// frogbot.config.ts
import { buildConfig } from 'frogbot'
import { agents } from './src/agents'

export default buildConfig({
  // secret, db, collections, and ai omitted
  agents
})
```

Slugs must be unique and URL-safe. Run `pnpm frogbot generate:types` to augment `GeneratedTypes` with configured agent slugs, matching collection typing; each configured model must resolve to a provider enabled under `ai.providers`.

## Invoke locally

Registered instances live at `frogbot.agents[slug]` and expose `generate` and `stream`.

```ts
const result = await frogbot.agents.support.generate({
  prompt: 'What is the status of ticket SUP-42?'
})

console.log(result.text)
```

Pass either a `prompt` or `messages`. Messages may be AI SDK `UIMessage[]` or `ModelMessage[]`; UI messages are converted before inference.

```ts
const result = await frogbot.agents.support.stream({
  messages: [
    {
      id: 'message-1',
      role: 'user',
      parts: [{ type: 'text', text: 'Help with ticket SUP-42' }]
    }
  ]
})

for await (const text of result.textStream) {
  process.stdout.write(text)
}
```

Local calls default to `overrideAccess: true`. To enforce the configured rule, pass a request and `overrideAccess: false`.

```ts
await frogbot.agents.support.generate({
  prompt: 'Review ticket SUP-42',
  req,
  overrideAccess: false
})
```

Local calls are stateless by default. Pass an existing `threadId` to `generate` to persist the new user message and assistant response against server-owned history.

```ts
await frogbot.agents.support.generate({
  prompt: 'Review ticket SUP-42 again',
  threadId,
  req,
  overrideAccess: false
})
```

Thread persistence accepts prompts or `UIMessage[]`; it does not accept `ModelMessage[]`. Local `stream()` calls remain stateless.

## Schedule runs

Add schedule triggers next to the agent that owns the recurring work. Each trigger requires a URL-safe slug, exactly one schedule form, and exactly one of `prompt` or `handler`.

```ts
export const reportingAgent: AgentConfig = {
  slug: 'reporting',
  model: 'fast',
  instructions: 'Analyze account activity and report anomalies.',
  triggers: [
    {
      type: 'schedule',
      slug: 'frequent-check',
      schedule: { every: '30m' },
      prompt: 'Check account activity and report any anomalies.'
    },
    {
      type: 'schedule',
      slug: 'daily-rollup',
      schedule: { cron: '0 0 * * *' },
      handler: async ({ agent, req, job }) => {
        await agent.generate({
          prompt: `Prepare the rollup scheduled for ${job.scheduledFor.toISOString()}`,
          req
        })
      }
    }
  ]
}
```

`every` accepts positive whole durations in seconds, minutes, hours, or days when they divide evenly into the corresponding cron field. Use `cron` for other intervals. Cron expressions use UTC; timezone-specific schedules are not yet supported.

Payload Jobs runs schedules and skips an occurrence while the same trigger already has an active or runnable scheduled job. User-defined jobs, workflows, queues, and automatic runners remain configured alongside FrogBot schedules.

Each prompt trigger creates a fresh thread with `user: null` and persists its user and assistant messages. A handler may invoke the owning agent, another agent, or no agent. Every handler receives `{ frogbot, agent, req, job }`, and `req.context` contains `source`, `agentSlug`, `triggerSlug`, and `jobId`. Removing an agent or trigger makes already-queued work for it complete without running.

## Invoke over HTTP

Configuring at least one worker mounts two Payload root endpoints. They are served under the normal `/api` prefix.

| Method | Path | Result |
| --- | --- | --- |
| `GET` | `/api/agents` | Accessible slugs as `{ agents: [{ slug }] }` |
| `POST` | `/api/agents/:slug` | Generated JSON or an AI SDK UI message stream |

POST exactly one non-empty `prompt` or non-empty `messages` array. Authenticated calls create a thread when `threadId` is absent. Without an explicit event-stream accept header, the response is `{ text, usage, finishReason, threadId }`.

```bash
curl http://localhost:3000/api/agents/support \
  --request POST \
  --header "Authorization: Bearer $FROGBOT_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{ "prompt": "Help with ticket SUP-42" }'
```

Request an AI SDK UI stream with `Accept: text/event-stream`.

```bash
curl http://localhost:3000/api/agents/support \
  --request POST \
  --header "Authorization: Bearer $FROGBOT_TOKEN" \
  --header "Content-Type: application/json" \
  --header "Accept: text/event-stream" \
  --data '{ "prompt": "Help with ticket SUP-42" }'
```

Stream responses return the thread ID in the `X-Frogbot-Thread-Id` header. Continue the conversation by sending that ID with only the next user message.

```bash
curl http://localhost:3000/api/agents/support \
  --request POST \
  --header "Authorization: Bearer $FROGBOT_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{ "prompt": "What changed since then?", "threadId": "THREAD_ID" }'
```

FrogBot loads stored history, rejects threads owned by another authenticated user, and rejects client-supplied assistant or system messages. Custom access rules can allow anonymous callers to create and continue threads, but those threads are not private to the anonymous caller who created them because there is no anonymous identity to verify. Applications handling sensitive conversations should require authentication.

Malformed input returns `400`, an unknown slug returns `404`, and an aborted request returns a bodyless `499`.

See [Chat persistence](/chat/overview) for collection customization and durability behavior.

## Control access

`access` receives `{ req }` and may return a boolean or promise. Its default is `Boolean(req.user)`.

```ts
access: ({ req }) => Boolean(req.user)
```

HTTP POST calls always set `overrideAccess: false`. The GET endpoint evaluates each worker's rule and omits denied entries or entries whose rule throws.

Custom rules may allow anonymous requests by returning `true`. Local calls bypass the rule unless you explicitly set `overrideAccess: false` with a request.

## Follow hooks

Worker runs use the five hooks configured under `ai.hooks`. Every hook receives `agent: { slug, runId }`, plus `req` and `user` when available.

`beforeOperation` and `afterOperation` run once for the whole generate or stream call. Agent HTTP calls use that same lifecycle rather than adding another one.

`beforeUpstream`, `afterUpstream`, and `afterError` run around each model's `doGenerate` or `doStream` call, so a tool loop can produce multiple upstream phase pairs.

Access is checked before `beforeOperation`, so denied calls run no hooks. Stream completion, failure, and abort each finalize `afterOperation` at most once.

Tool execution has no separate lifecycle hook in v0. Match `ToolCtx.agent.runId` with the hook argument's `agent.runId` to correlate tool work.

See [AI hooks](/configuration/ai#observe-calls) for phase arguments, mutation rules, and failure isolation.
