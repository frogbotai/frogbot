Environment Variables are a way to store sensitive information that your application needs to function. This could be anything from API keys to [Database](/database/overview) credentials. FrogBot allows you to easily use Environment Variables within your config and throughout your application.

## Next.js Applications

If you are using Next.js, no additional setup is required other than creating your `.env` file.

To use Environment Variables, add a `.env` file to the root of your project:

```plaintext
project-name/
├─ .env
├─ package.json
├─ frogbot.config.ts
```

Here is an example of what an `.env` file might look like:

```plaintext
SERVER_URL=localhost:3000
DATABASE_URL=mongodb://localhost:27017/my-database
```

To use Environment Variables in your FrogBot Config, you can access them directly from `process.env`:

```ts
import { buildConfig } from 'frogbot'

export default buildConfig({
  serverURL: process.env.SERVER_URL,
  // ...
})
```

## Typed environment variables

Use `defineEnv` to parse and validate your server-side environment when your application starts. It reports all invalid or missing variables together and returns a typed, frozen object.

Create `src/env.ts`:

```ts
import { defineEnv, env, frogbotEnv } from 'frogbot/env'

export const envService = defineEnv({
  ...frogbotEnv,
  emailEnabled: env.boolean().default(false),
  smtpUrl: env
    .string()
    .requiredWhen((values) => values.emailEnabled === true),
})
```

Then use the resolved values in your FrogBot config:

```ts
import { buildConfig } from 'frogbot'

import { envService } from './env.js'

export default buildConfig({
  secret: envService.frogbotSecret,
  client: {
    url: envService.databaseUrl,
  },
})
```

This replaces fallback expressions such as `process.env.FROGBOT_SECRET || ''` with values that have already been validated.

### Builders and modifiers

The `env` factory provides these builders:

| Builder | Result |
| --- | --- |
| `env.string()` | String value |
| `env.number()` | Number value |
| `env.boolean()` | Boolean value |
| `env.enum(['one', 'two'])` | One of the listed strings |
| `env.custom(parse)` | Value returned by your parser |

Chain builders with `.default(value)`, `.required()`, `.requiredWhen(predicate)`, or `.name('CUSTOM_NAME')`. A variable cannot have both a default and a required modifier. Required predicates receive all values resolved during the first parsing pass.

`frogbotEnv` includes these common builders:

| Property | Environment variable | Behavior |
| --- | --- | --- |
| `nodeEnv` | `NODE_ENV` | `development`, `production`, or `test`; defaults to `production` |
| `logLevel` | `LOG_LEVEL` | `trace`, `debug`, `info`, `warn`, `error`, `fatal`, or `silent`; defaults to `info` |
| `port` | `PORT` | Number; defaults to `3000` |
| `frogbotSecret` | `FROGBOT_SECRET` | Required string |
| `databaseUrl` | `DATABASE_URL` | Required string |

You can replace a base builder after spreading `frogbotEnv`:

```ts
const envService = defineEnv({
  ...frogbotEnv,
  port: env.number().default(4000),
})
```

### Names and parsing

Property names become uppercase environment variable names with underscores before uppercase letters. For example, `apiUrl` becomes `API_URL`, `gitSha1` becomes `GIT_SHA1`, and `s3Bucket` becomes `S3_BUCKET`. Use `.name()` when the environment variable follows another convention.

Empty strings count as unset values. This is stricter than provider SDKs that may accept an empty API key as present.

Numbers use JavaScript number parsing, so `PORT=0` resolves to `0` and invalid numbers fail validation. Boolean parsing is case-insensitive and accepts:

- True: `1`, `on`, `t`, `true`, `y`, `yes`
- False: `0`, `f`, `false`, `n`, `no`, `off`

Other boolean values fail validation.

When `NODE_ENV=test`, required checks are skipped so tests do not need every application secret. Present values are still parsed and can still produce validation errors.

## Client-side Environments

For security and safety reasons, the [Admin Panel](/admin/overview) does **not** include Environment Variables in its _client-side_ bundle by default. But, Next.js provides a mechanism to expose Environment Variables to the client-side bundle when needed.

If you are building a [Custom Component](/custom-components/overview) and need to access Environment Variables from the client-side, you can do so by prefixing them with `NEXT_PUBLIC_`.

<Warning>
  **Important:** Be careful about what variables you provide to your client-side
  code. Analyze every single one to make sure that you're not accidentally
  leaking sensitive information. Only ever include keys that are safe for the
  public to read in plain text.
</Warning>

For example, if you've got the following Environment Variable:

```bash
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY=pk_test_XXXXXXXXXXXXXXXXXX
```

This key will automatically be made available to the client-side FrogBot bundle and can be referenced in your Custom Component as follows:

```tsx
'use client'
import React from 'react'

const stripeKey = process.env.NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY

const MyClientComponent = () => {
  // do something with the key

  return <div>My Client Component</div>
}
```

For more information, check out the [Next.js documentation](https://nextjs.org/docs/app/building-your-application/configuring/environment-variables).

## Outside of Next.js

If you are using FrogBot outside of Next.js, we suggest using the [`dotenv`](https://www.npmjs.com/package/dotenv) package to handle Environment Variables from `.env` files. This will automatically load your Environment Variables into `process.env`.

To do this, import the package as high up in your application as possible:

```ts
import dotenv from 'dotenv'
dotenv.config()

import { buildConfig } from 'frogbot'

export default buildConfig({
  serverURL: process.env.SERVER_URL,
  // ...
})
```

<Warning>
  **Tip:** Be sure that `dotenv` can find your `.env` file. By default, it will
  look for a file named `.env` in the root of your project. If you need to
  specify a different file, pass the path into the config options.
</Warning>
