A turn is one run of the agent in response to a user message, from the first model step to the final reply. FrogBot runs at most one turn per chat at a time, whether the message comes from the admin chat, `@frogbotai/ui`, an HTTP client, a channel, or `agent.generate()`.

Local `agent.generate({ chatId })` calls do not queue. If the chat already has a turn in progress, the call rejects with a `turn-in-progress` error.

## Turn states

| State | Meaning |
| --- | --- |
| `idle` | No turn is running; the next user message starts one |
| `running` | The agent is working on a reply |
| `awaiting` | The reply is paused at a [question](/chat/questions) or another client tool call |

The `pending` endpoint reports the current state as `state`. A turn moves from `awaiting` back to `running` when the last pending call in the step is answered through the chat or the `settle` endpoint, and to `idle` when a call is dismissed. If the waiting assistant message is deleted, the chat returns to `idle`.

## Messages sent during a turn

A user message that arrives while a turn is `running` or `awaiting` is saved as a queued message instead of starting a second run. Queued messages are part of the chat, but they are not sent to the model until they are promoted.

JSON requests receive `202 Accepted`:

```json
{ "status": "queued", "chatId": "CHAT_ID", "messageId": "MESSAGE_ID", "delivery": "queue" }
```

Stream requests receive a single transient `data-queued` part with the same `messageId` and `delivery`. The `X-FrogBot-Chat-Id` header is set in both cases.

When the current turn ends, FrogBot promotes the oldest queued message and runs it as the next turn, as the user who sent it and with the model and reasoning option it was sent with. The next queued message waits for that turn to end. Messages sent while a question is waiting stay queued until the question is answered or dismissed, so answer the question first to run them.

A turn that continues after a question is answered uses the model and reasoning option of the chat's latest user message, not the ones sent with the answer. If a stored model or reasoning option is no longer offered when its turn runs, for example after a configuration change, the turn fails with `code: "selection-unavailable"` before calling the model. FrogBot never substitutes another model or option.

In the chat UI, a queued message shows a queued indicator, and the chat reloads when the turn ends so the promoted turn appears once it is saved.

## Steer a running turn

Send `delivery: "steer"` to add a message to the turn that is already running instead of waiting for it to finish.

```bash
curl http://localhost:3000/api/agents/support \
  --request POST \
  --header "Authorization: Bearer $FROGBOT_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{ "prompt": "Only look at last week", "chatId": "CHAT_ID", "delivery": "steer" }'
```

FrogBot adds a steer message to the model's messages at the next step boundary, so the agent sees it before its next model call. From that step on, the turn uses the steer message's model and reasoning option.

Steering applies only when the sender is the user who drives the current run:

- The sender of the message being answered.
- The user who answered the question that the turn is continuing from.

A steer from anyone else, or one that arrives after the last step, runs as an ordinary queued message.

A steer that joins a turn is stored just before that turn's reply, so history reads in the order the model saw it.

A steer is never treated as the answer to a pending question.

## Edit or remove a queued message

The author of a queued message can change it before it is promoted.

```bash
curl http://localhost:3000/api/agents/support/chats/CHAT_ID/messages/MESSAGE_ID \
  --request PATCH \
  --header "Authorization: Bearer $FROGBOT_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{ "parts": [{ "type": "text", "text": "Only look at yesterday" }], "delivery": "steer" }'
```

Send `parts`, `delivery`, or both. A `DELETE` request to the same path removes the message and returns `204 No Content`. Both return `403` for anyone other than the author, and `409` with `code: "not-queued"` once the message has been promoted.

## Compaction

Every turn sends the chat's messages to the model, so a long chat eventually outgrows the model's context window.

1. **Estimate.** Before each model step, FrogBot estimates the prompt size. It takes the prompt tokens that the provider measured for the previous step, or for the chat's latest reply, and adds about one token per four characters of everything since.
2. **Compact.** When the estimate reaches the ceiling, FrogBot summarizes the older messages first. The ceiling is the context window less [`ai.compaction.buffer`](/ai/overview#compaction-options).

A provider's "too long" rejection also compacts once and retries the step. A second rejection ends the turn with `This chat is too long for <model ID>.`

Compaction works the same for the admin chat, HTTP clients, channels, and `agent.generate({ chatId })`. Runs without a `chatId` never compact. A model with no known window, neither a catalog entry nor a custom model's `limit.input` or `limit.context`, compacts only on a "too long" rejection.

The summary is written by the chat's own model, through `req.frogbot.generateText`, so AI hooks and usage logging see it. It follows a fixed template (objective, requirements, decisions, work state, next move, relevant records and links, important context). The summary request has no tools, so the older messages' tool calls and results reach it as text. After compaction the model gets:

1. One user message holding the summary in a `<conversation-checkpoint>`.
2. The newest messages, about [`keep`](/ai/overview#compaction-options) tokens' worth, whole, with their files and tool results. They start at a user message and always include the latest exchange.
3. Everything after them, including this turn's steps, steered messages, and an answered question or tool approval.

A later compaction summarizes the previous summary with the messages since. Stored messages don't change: the admin chat, the messages collection, and [branches](/chat/ui-chat#message-actions) still show every message.

The summary is saved as a `data-compaction` part. Its fields are `status` (`running`, `completed`, or `failed`), `reason` (`auto` or `manual`), `summary`, `error`, `tokens`, and `keepFrom`, the ID of the first kept message.

- An automatic compaction is part of the reply it ran for. It streams from `running` to its result between that reply's steps.
- If the summary fails, the part is saved as `failed` and the turn ends with its error. The next turn tries again.
- Channels post only the reply, never the summary.

Compact a chat now with `/compact` in the admin chat, or with a request. It works with `auto: false`, needs [write access](/chat/overview#who-can-write-a-chat) to the chat, and saves an assistant message that holds only the `manual` part:

```bash
curl http://localhost:3000/api/frogbot/chat/compact \
  --request POST \
  --header "Authorization: Bearer $FROGBOT_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{ "chatId": "CHAT_ID" }'
```

It returns `{ "message": … }`. A chat whose turn is running or waiting for an answer returns `409` with `code: "turn-in-progress"`, and one with only a single exchange returns `409` with `code: "nothing-to-compact"`. Neither writes anything.

## Channels

Channel messages follow the same rules. A message posted while the bot is replying in a thread is queued, and nothing is posted for it until it is promoted. When the channel runs in the same process, FrogBot posts the promoted reply to the same thread; otherwise the reply is saved to the chat without being posted.

A channel chat is continued only from its channel. Its owner can read it in the admin chat, but web and HTTP messages, answers, and dismissals are refused with `409` and `code: "channel-chat"`, so nothing is queued behind a channel turn from outside the thread. A channel chat that has no FrogBot owner cannot be opened from the web at all. See [who can write a chat](/chat/overview#who-can-write-a-chat).

## Crash recovery

FrogBot saves the assistant message after every model step, so a reply keeps every step that finished before a failure. When a stream is aborted or fails, FrogBot also saves the partial step and marks its unfinished tool calls as errors.

A running turn holds a lease that is renewed while the agent works. If the process stops, the step in progress is lost and the lease expires after about a minute. The next message then starts a new turn, unless the last saved step asked a question: that question is still waiting after a restart, can be answered normally, and new messages queue behind it.

## Limitations

- FrogBot does not guarantee exactly-once side effects. If a process stops between a tool's execution and the next checkpoint, that step is not saved, and the tool can run again if a later turn repeats the call.
- Queued messages are promoted when a turn ends. A message queued behind a turn that was interrupted by a crash runs after the next turn in that chat ends.
- The chat UI shows a promoted turn when it has been saved. It does not stream a promoted turn live into an open chat, and a tab only notices a turn started elsewhere when it reloads.
- Chats without an owner are shared by every anonymous caller who knows the chat ID. Any of them can answer or dismiss its questions, steer its turns, and edit its queued messages.
- Turn coordination requires the SQLite, PostgreSQL, or MongoDB adapter.
