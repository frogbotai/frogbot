When you configure an agent, FrogBot stores authenticated HTTP conversations in FrogBot collections. You can use the default `chats` and `messages` collections without adding configuration, or adopt the roles into your own collections.

Anonymous agent calls remain stateless, even when a custom agent access rule allows them.

Agent calls use `/api/agents/<slug>`. To call the embedded AI gateway directly, see the [authenticated HTTP endpoints](/configuration/ai#call-over-http).

## Use the default collections

FrogBot injects both collections when agents are configured and no collection claims either role.

| Collection | Stored fields |
| --- | --- |
| `chats` | `title`, `user`, `agent`, `lastMessageAt` |
| `messages` | Text `id`, `chat`, `role`, `parts`, `metadata`, `usage` |

Chat and message collections use soft deletion and appear under **Chat** in the admin panel. Access is owner-scoped through the chat's `user` relationship.

Messages store the AI SDK `UIMessage.parts` array. Tool calls, tool results, reasoning, and custom data parts therefore remain available on later turns instead of being flattened into text.

## Use the default chat views

When an agent is configured, the admin dashboard and chat collection create route open an empty chat with the first configured agent. Sending the first message creates the chat and updates the URL to its document route without remounting the conversation.

The chat collection list uses the standard collection list view, so filtering, sorting, and columns behave like any other collection. Selecting a chat opens its document view, restores up to 500 stored messages in chronological order, and continues the same conversation.

These defaults also apply when your own collection uses `chat: true`. FrogBot uses that collection's slug for create, list, and document routes.

## Customize admin chat components

Use `admin.components.chat` for chat-wide component overrides. `Chat` replaces the canonical chat surface on both the dashboard and chat document routes. `Greeting` replaces the block shown above the composer while a chat has no messages. The role-specific action slots receive the current message, pending state, and `defaultActions`.

```ts
import { buildConfig } from 'frogbot'

export default buildConfig({
  // required options omitted
  admin: {
    components: {
      chat: {
        Chat: '/components/WorkspaceChat#WorkspaceChat',
        Greeting: '/components/WorkspaceGreeting#WorkspaceGreeting',
        UserMessageActions: '/components/UserMessageActions#UserMessageActions',
        AssistantMessageActions:
          '/components/AssistantMessageActions#AssistantMessageActions'
      }
    }
  }
})
```

Each entry can also use a component definition with `clientProps`. Use the role slots for small additions or replacements. Use `Chat` when you need to replace the conversation shell while retaining FrogBot's default route loading and navigation.

## Greeting an empty chat

A chat with no messages shows a greeting above the composer. It renders the active agent's avatar when the agent profile sets one, and otherwise falls back to the logo from `admin.components.graphics.Logo`, so a custom logo appears without extra configuration. The greeting line varies by time of day and includes the signed-in user's name when the user record has one.

`Greeting` receives `avatar`, `logo`, `name`, and `userName`, so an override can reuse those values or ignore them entirely.

## Override the chat views

Set collection view components under `admin.components.views`. FrogBot only defaults the edit root view on the `chat: true` collection and preserves a configured override.

```ts
import type { CollectionConfig } from 'frogbot'

export const Conversations: CollectionConfig = {
  slug: 'conversations',
  chat: true,
  fields: [],
  admin: {
    components: {
      views: {
        edit: {
          root: {
            Component: '/components/Conversation#Conversation'
          }
        }
      }
    }
  }
}
```

Override a route view when you need to replace its surrounding page behavior instead of only the chat surface. The dashboard path must remain `/`.

```ts
import { buildConfig } from 'frogbot'

export default buildConfig({
  // required options omitted
  admin: {
    components: {
      views: {
        dashboard: {
          Component: '/components/Dashboard#Dashboard',
          path: '/'
        }
      }
    }
  }
})
```

## Customize the collections

Add `chat: true` or `message: true` to adopt a collection. FrogBot keeps your slug and merges in its required fields, hooks, access rules, and admin defaults.

```ts
import type { CollectionConfig } from 'frogbot'

export const Conversations: CollectionConfig = {
  slug: 'conversations',
  chat: true,
  fields: [
    {
      name: 'channel',
      type: 'select',
      options: ['web', 'support']
    }
  ]
}

export const Turns: CollectionConfig = {
  slug: 'turns',
  message: true,
  fields: []
}
```

Your field definitions win when they are compatible with the base schema. FrogBot appends missing base fields and combines hooks. It rejects incompatible field types and protects these fields:

- `chats.user`
- `messages.id`
- `messages.chat`
- `messages.parts`

Mark at most one collection for each role. If an unmarked collection already uses the default `chats` or `messages` slug, sanitization asks you to mark or rename it rather than adopting it implicitly.

## Continue a chat

The first authenticated HTTP request creates a chat and returns its ID.

```bash
curl http://localhost:3000/api/agents/support \
  --request POST \
  --header "Authorization: Bearer $FROGBOT_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{ "prompt": "Review campaign performance" }'
```

JSON responses include `chatId`. Stream responses provide the same value in `X-Frogbot-Chat-Id`.

Send that ID with only the next user message. FrogBot loads and validates stored history before running the agent.

```bash
curl http://localhost:3000/api/agents/support \
  --request POST \
  --header "Authorization: Bearer $FROGBOT_TOKEN" \
  --header "Content-Type: application/json" \
  --data '{ "prompt": "Now compare it with last week", "chatId": "CHAT_ID" }'
```

FrogBot rejects a chat owned by another user. It also rejects client-supplied assistant or system messages; only the server persists assistant output.

## Persist local generation

Local generation is stateless unless you provide an existing chat ID.

```ts
const result = await frogbot.agents.support.generate({
  prompt: 'Check the latest campaign changes',
  chatId,
  req,
  overrideAccess: false
})
```

`generate({ chatId })` persists the new user message, loads stored history, runs the agent, and stores the resulting assistant message. Local `stream()` calls remain stateless.

## Understand durability

FrogBot awaits the user-message write before inference begins. Streaming responses save finalized or partial assistant parts on completion, error, abort, or client disconnect. Usage is attached when the model emits it but never blocks the message save.

<Warning>
  FrogBot's SQLite adapter disables transactions unless you configure `transactionOptions`. Without transactions, a failure between chat creation and the first message write can leave an empty chat. MongoDB and transaction-enabled adapters roll back the pair.
</Warning>

A hard process exit during inference can still leave a user message without an assistant reply. The chat remains valid and can be continued; incremental part persistence and resumable streams are planned separately.
