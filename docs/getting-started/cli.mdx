The `frogbot` package installs a `frogbot` command. Run it from your app's root directory through your package manager, for example `pnpm frogbot dev` or `npx frogbot dev`.

```bash
pnpm frogbot generate:types
```

- **Environment files:** Before any command runs, `frogbot` loads `.env*` files from the current directory using Next.js rules (development files unless `NODE_ENV` is `production`).
- **Config discovery:** Commands that load your app look for `frogbot.config.{ts,js,mjs}` in the current directory, `src/`, a parent directory, or the path in `FROGBOT_CONFIG_PATH`.
- **Exit codes:** Command names are case-insensitive. A missing or unknown command prints available commands (and points to [Plugin commands](#plugin-commands)) and exits with code `2`. A command that fails prints the error and exits with code `1`.

## Check your config

`frogbot check` loads your config in runtime mode, the way `start` and the running app do, and waits for it to finish sanitizing. It starts no server, runs no `onInit`, opens no database and writes no file, so it's safe to run after every edit. It exits `0` when everything passes and `1` when it finds a problem.

```bash
$ pnpm frogbot check
[frogbot] TYPES_STALE frogbot-types.ts: out of date; run `frogbot generate:types`
[frogbot] 1 issue found
```

Each problem is one line on stderr, `[frogbot] <code> <path>: <message>`, followed by a count:

| Code | Means | Fix |
| --- | --- | --- |
| `CONFIG_INVALID` | The config failed to load or sanitize, for example an agent model no provider serves or a duplicate collection slug. The message is the error the running app would throw. The checks below need a loaded config, so they're skipped. | Fix the error, then run `check` again. Config errors show one at a time. |
| `INVALID_CRON` | A task or workflow `schedule[].cron` isn't a valid cron expression. The path names it, for example `jobs.tasks.sendDigest.schedule.0.cron`. | Fix the expression. |
| `UNKNOWN_TASK` | A workflow whose `handler` is an array of steps has a step whose `task` isn't in `jobs.tasks`. | Add the task, or fix the slug. |
| `TYPES_STALE` | `frogbot-types.ts` is missing or doesn't match your config. | Run `frogbot generate:types`. |
| `IMPORT_MAP_STALE` | The admin import map doesn't match the components your config references. Skipped when `admin.importMap.autoGenerate` is `false` or the app has no admin folder. | Run `frogbot generate:importmap`. |

`INVALID_CRON` and `UNKNOWN_TASK` are config errors, so `dev` and `start` fail on them too.

`check` also warns about things that don't stop your app. A warning is one line on stderr, `[frogbot] warning <code> <path>: <message>`, and doesn't change the exit code; a passing run says `check passed with N warnings`:

| Code | Means | Fix |
| --- | --- | --- |
| `MISSING_ICON` | A collection that shows in the sidebar has no `admin.icon`, so it shows a folder. Collections with `admin.hidden`, `admin.group: false` or `auth` are skipped. The path names it, for example `collections.invoices`. | Set `admin.icon` to one of the [built-in names](/admin/admin-navigation#collection-icons-and-placement). |

`check` doesn't run TypeScript or look at the database. When it passes, it says so: run your app's `typecheck` script for type errors, and `frogbot migrate:status` for pending migrations.

### JSON output

With `--json`, `check` writes exactly one JSON object to stdout and sends everything else, including your config's own logs, to stderr:

```json
{ "command": "check", "success": true }
```

When there are warnings, a `warnings` array of `{ code, path, message }` entries sits beside `success`, whether it's `true` or `false`.

```json
{
  "command": "check",
  "success": false,
  "error": {
    "code": "CHECK_FAILED",
    "message": "1 issue found",
    "issues": [
      {
        "code": "INVALID_CRON",
        "path": "jobs.tasks.sendDigest.schedule.0.cron",
        "message": "Task 'sendDigest' schedule 0 has an invalid cron expression: 'nope'."
      }
    ]
  }
}
```

An issue has no `path` when it isn't tied to one place in the config, as with `CONFIG_INVALID`.

## Deploy

```bash
pnpm frogbot deploy docker --dry-run
```

`frogbot deploy <target>` runs every check first, prints all the problems at once and exits `1` before changing anything; then it builds and deploys with your own login for the host. Core ships `docker`, `fly`, `gcp`, `aws` and `azure`, and [`dojo()`](/plugins/dojo) adds `dojo`, which runs when you name no target. See [Deployment](/deployment/overview) for each target's flags, checks, what it creates and how to remove it.

### Plugin deploy targets

A plugin adds a target under `cli.deployTargets`, the way `dojo()` adds `dojo`; app developers don't write one. Names are lowercase letters, digits and dashes, and can't be a core target's name.

```ts
import type { DeployTarget, Plugin } from 'frogbot'

const myHost: DeployTarget = {
  describe: 'Deploy to My Host',
  preflight: async ({ io }) =>
    (await io.which('myhost'))
      ? []
      : [{ code: 'TOOL_MISSING', message: '`myhost` isn\'t installed.', fix: 'Install it from https://myhost.dev/cli' }],
  run: async ({ run, log }) => {
    await run('myhost', ['deploy'])
    log('[frogbot] Deployed.')
  },
}

export const myHostPlugin: Plugin = (config) => ({
  ...config,
  cli: { ...config.cli, deployTargets: { ...config.cli?.deployTargets, 'my-host': myHost } },
})
```

`frogbot deploy` parses the shared flags, runs its checks and the target's `preflight`, and calls `run` only when none fails. Both get one context:

| Field | Type | Description |
| --- | --- | --- |
| `root` | `string` | The app's folder. |
| `config` | `DeployConfig` | The loaded config's collections, database adapter and jobs. |
| `flags` | `{ dryRun, json, interactive }` | The shared flags; `interactive` is false with `--no-interactive`, `--json` or no terminal. |
| `args` | `string[]` | The arguments left after the target name and the shared flags. |
| `env` | `Record<string, string>` | The app's production variables. |
| `io` | `DeployIO` | The terminal, prompts, `exec` and `which`. Use `io.exec` for read-only queries. |
| `log` | `(line) => void` | Prints a line, on stderr with `--json`. |
| `run` | `(command, args, options?) => Promise<…>` | Runs a command that changes something; prints it instead on `--dry-run`, and throws on a non-zero exit. `options.input` goes to stdin and `options.mask` hides values when the command is printed. |
| `writeFile` | `(path, contents) => Promise<void>` | Writes a file in the app; prints the path instead on `--dry-run`. |

`preflight` returns `PreflightIssue[]` (`{ code, message, fix }`) and must not change anything. Whatever `run` returns becomes `result` in `--json` output.

## Plugin commands

Plugins and your config can register custom CLI commands under `cli.commands`. Each key is a lowercase command name, and each value is an async or sync handler that runs when you call `frogbot <name>`.

```ts
import { buildConfig } from 'frogbot'

export default buildConfig({
  // ...
  cli: {
    commands: {
      'users:count': async ({ getFrogBot }) => {
        const frogbot = await getFrogBot()
        const { totalDocs } = await frogbot.count({ collection: 'users' })

        console.log(totalDocs)
      },
    },
  },
})
```

When your app has a config file, `frogbot` loads it before running any command and passes the handler one context object:

| Field | Type | Description |
| --- | --- | --- |
| `args` | `string[]` | Arguments passed after the command name. |
| `command` | `string` | The name the command was invoked as. |
| `getConfig` | `() => Promise<FrogBotSanitizedConfig>` | Resolves to the sanitized config `frogbot` already loaded. |
| `getFrogBot` | `(options?) => Promise<FrogBot>` | Boots a FrogBot instance on first call, reuses it on later calls, and destroys it when the command finishes. Accepts `init` options (excluding `config`). |

<Accordion title="Execution lifecycle, overrides, and error handling">
  - **Completion & exit codes:** `frogbot` exits when your handler's promise resolves (using `process.exitCode` if set, otherwise `0`), so `await` all async work. Throwing an error prints the message and exits with code `1`.
  - **Overriding & merging:** A `cli.commands` entry with the same name as a built-in command replaces it. Plugins should spread existing commands (`cli: { ...config.cli, commands: { ...config.cli?.commands, 'my:command': handler } }`) so user commands are preserved.
  - **Validation:** Command names containing uppercase letters or non-function handlers fail config validation. If the config file fails to load, built-in commands still run while plugin commands print the load error and exit with code `1`.
  - **Unknown commands:** Running an unknown command prints `[frogbot] "<name>" isn't a command in this app.` (or `[frogbot] "<name>" isn't a built-in command, and there's no app here to add it.` when no config file is found) and exits with code `2`.
</Accordion>

### Commands from `dojo()`

Apps created with `create-frogbot-app` list [`dojo()`](/plugins/dojo), which adds `frogbot dojo`: every Dojo action from the terminal, for people and coding agents. Without an app (such as when pulling an app into an empty directory), run the same commands as `npx @frogbotai/plugin-dojo <command>`.

| Command | Description |
| --- | --- |
| `login`, `logout`, `whoami` | Signs in with a browser code (the first sign-in makes the account), signs out, or shows who is signed in. |
| `workspaces`, `members` | Lists, creates and renames workspaces, and manages their members. |
| `apps share`, `apps pull`, `apps logs` | Shares the app in this folder, downloads one, or prints its logs. See [`dojo apps share`](#dojo-apps-share). |
| `apps list`, `get`, `create`, `rename`, `delete` | Manages your apps. |
| `deployments`, `env`, `domains`, `sharing` | An app's deployments and build logs, environment keys, custom domain, and who it's shared with. |
| `keys`, `billing` | Your Dojo API keys, and the workspace's plan and billing link. |

Every command takes `--json`, which prints one JSON value on stdout, and reads `FROGBOT_DOJO_TOKEN` as its API key. Destructive commands need `--yes` without a terminal. `frogbot dojo --help` lists everything; the [Dojo plugin](/plugins/dojo#commands) has the full list with examples.

### `dojo apps share`

```bash
npx frogbot dojo apps share --no-data
```

Uploads the app in the current folder to Dojo, streams `[build]` logs, and prints a share link followed by the live `https://<name>.frogbot.app` URL. `npx frogbot share` is the same command, with the same flags. Run it from the folder containing `frogbot.config.ts` (or its parent when the config is inside `src/`). In an app without `dojo()`, run `npx @frogbotai/plugin-dojo apps share`.

`share` and [`frogbot deploy dojo`](#deploy) run the same code, so `share` also takes `--dry-run` (lists the files, size, keys and data it would send, and makes no request), `--json`, `--no-interactive` and `--env-file`.

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `--app` | app slug or id | — | Ships to this existing app and links the folder to it in `.frogbot/app.json`, for a fresh clone or CI. Stops if the folder is linked to another app. Can't be combined with `--workspace` or `--name`. |
| `--data` | flag | — | On the first share, uploads local SQLite data and files without prompting. |
| `--no-data` | flag | — | On the first share, uploads code only without prompting. |
| `--workspace` | workspace slug | — | Dojo workspace to create the app in on first share (when you belong to multiple). |
| `--name` | name | `package.json` `name` | Subdomain slug for `https://<name>.frogbot.app` on first share (lowercased, alphanumeric + dashes). |
| `--no-keys` | flag | — | Uploads no `.env` keys. |
| `--skip-key` | key name (repeatable) | — | Excludes a specific key (case-sensitive), e.g. `--skip-key STRIPE_KEY`. Unknown key names exit with code `2`. |
| `--yes` | flag | — | On the first share, uploads all detected keys without the interactive checklist. |
| `--update-keys` | flag | — | On subsequent shares, overwrites live keys whose local values differ. |

<AccordionGroup>
  <Accordion title="Pre-flight checks & signing in">
    - **Lockfile check:** `share` stops before uploading with `NO_PACKAGE_JSON` or `NO_LOCKFILE` if `package.json` is missing, if the app uses Bun, or if no `pnpm-lock.yaml`, `package-lock.json`, or `yarn.lock` is present.
    - **Browser login:** On first use, `share` prints a Dojo verification URL that carries the code, then the code itself (and opens your browser in interactive terminals). When the code expires, `share` starts a new one: on its own in a non-interactive shell (up to three codes), or when you press Enter. Your token is saved in `~/.config/frogbotai/auth.json` (or `$XDG_CONFIG_HOME`) with owner-only permissions.
    - **API key instead:** Set `FROGBOT_DOJO_TOKEN` to a Dojo API key (from `frogbot dojo keys create`) for CI and agents. It's used ahead of the stored token, and a refused one fails instead of starting a browser login. In CI (`CI` set, no terminal) with no token and no stored sign-in, `share` exits `1` at once naming `FROGBOT_DOJO_TOKEN` instead of printing a code nobody can open.
    - **Custom Dojo endpoint:** Set `FROGBOT_DOJO_URL` to target a different Dojo instance.
  </Accordion>
  <Accordion title="First share vs. subsequent updates">
    - **First share:** Creates a Dojo app named after `package.json`'s `name` (or `--name`), writes the app ID to `.frogbot/app.json`, and adds `/.frogbot` to `.gitignore`.
    - **Paying for the app:** When the workspace's Dojo plan doesn't cover the app yet, `share` prints Dojo's upgrade link (and opens it in interactive terminals), waits up to 30 minutes for the payment, then carries on with the same share.
    - **Later shares:** Deploying again from the same folder ships a new version of the linked app. Delete `.frogbot/app.json` to deploy as a brand-new app. In a folder with no link, such as a fresh clone or a CI job, `share --app <slug>` ships to that app and writes the link.
    - **Name collisions & workspaces:** If the app name is taken on Dojo, `share` prompts you to rerun with `--name <another name>`. If you belong to multiple workspaces in a non-interactive shell, pass `--workspace`. With no workspace yet, `share` says where to create one; in an interactive terminal it opens that page and checks again when you press Enter.
  </Accordion>
  <Accordion title="Bringing local database & upload files (--data)">
    - **First share only:** On the first share of a local `file:` SQLite app, `share` asks `Bring your data? 42 deals, 3 users, 12 files` (or requires `--data` / `--no-data` when non-interactive). Once a version of the app has started on Dojo, later shares deploy code only and never overwrite live data.
    - **Safe live copy:** `share` copies your SQLite database so it works while `frogbot dev` is running, stripping local-only state (queued jobs, locks, sessions, trigger subscriptions) while preserving users, password hashes, and `FROGBOT_SECRET` so existing connections keep working.
    - **Upload collections:** Files inside upload directories within your project root are uploaded with progress output and automatic 3x retries. `.env*`, `.git`, `node_modules`, and database files inside upload folders are excluded.
  </Accordion>
  <Accordion title="Environment keys (--no-keys, --skip-key, --update-keys)">
    - **Encryption & masking:** Keys from `.env*` files are masked in terminal output (`STRIPE_KEY ••••4242`) and sealed to Dojo's public key before leaving your machine. Platform variables (`DATABASE_URL`, `FROGBOT_SECRET`, `NODE_ENV`, `PORT`, `HOSTNAME`) are managed by Dojo automatically, and the Dojo sign-in (`FROGBOT_DOJO_TOKEN`, `FROGBOT_DOJO_URL`) never leaves your machine.
    - **First vs. later shares:** The first share lets you untick any keys interactively (or uploads all keys when non-interactive). Later shares add newly introduced keys automatically and keep existing live values unless you pass `--update-keys`.
    - **Editors:** Collaborators with editor access (such as from [`dojo apps pull`](#dojo-apps-pull)) deploy code only; key changes are restricted to workspace owners.
  </Accordion>
  <Accordion title="Uploaded files, 100 MB limit, and exit codes">
    - **Included files:** Uploads all tracked and untracked working files that are not ignored by `.gitignore` (up to **100 MB**).
    - **Always excluded:** `.git`, `.frogbot/`, `.env*`, `frogbot.db*`, `*.sqlite*`, `node_modules`, `.next`, `files/`, upload collection folders, and symlinks.
    - **Exit codes:** Build or upload failures print the last build lines and exit with code `1`. Invalid flag combinations (such as `--data` with `--no-data`) exit with code `2`.
  </Accordion>

### `dojo apps pull`

```bash
npx @frogbotai/plugin-dojo apps pull deals
```

Downloads the live code of a Dojo app you own or edit into a new `./<app>` directory, links `.frogbot/app.json` so running `npx frogbot dojo apps share` from that folder updates the same app, and writes a fresh local `.env` (`DATABASE_URL=file:./frogbot.db` and `FROGBOT_SECRET`). Live data and production secrets remain on Dojo.

```bash
cd deals
pnpm install
pnpm dev
```

- Refuses to overwrite an existing folder.
- Exits with code `1` if you lack editor/owner permissions or the app has no live version yet, and code `2` if no app slug is passed.

### `dojo apps logs`

```bash
npx @frogbotai/plugin-dojo apps logs deals --follow
```

Prints recent logs (last 24 hours, oldest first) for a Dojo app you own or edit, masking any stored secret values of 8+ characters as `••••`. Pass `--follow` to stream new lines every 2 seconds until Ctrl+C.

### `dojo logout`

```bash
npx @frogbotai/plugin-dojo logout
```

Revokes the CLI's key in Dojo and removes it from `auth.json`. Keys the CLI made with `frogbot dojo keys create` keep working; revoke them with `frogbot dojo keys revoke <id>`, which also revokes the keys that key made unless you pass `--no-cascade` (`--cascade`, the default, says so explicitly). If Dojo cannot be reached, the local file is kept so you can retry `logout`.

## `dev` and `start`

```bash
frogbot dev --port 4000
```

`frogbot dev` regenerates the admin import map, then runs `next dev`. `frogbot start` checks the import map, warns if `frogbot generate:importmap` is needed, and runs `next start`. Set `admin.importMap.autoGenerate` to `false` in `frogbot.config.ts` to skip the import map step.

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| Any Next.js argument | Next.js `dev` or `start` arguments | — | Forwarded to Next.js unchanged (for example `--port 4000` or `--webpack`). |

Requires `next.config.{ts,mjs,js,cjs}` and `next` in the current directory (`typescript` is also required at startup when using `next.config.ts`). Forwards `SIGINT`/`SIGTERM` and exits with Next.js's exit code.

With SQLite, `frogbot dev` and `frogbot run` keep the database's schema in step with your config the same way `frogbot up` does: outside production, FrogBot adds tables, columns and indexes and never drops data or asks; removed fields stay hidden; a change that would lose data is skipped with an error line. See [Prototyping in development mode](/database/sqlite#prototyping-in-development-mode). `withFrogBot` also turns off the rules Next.js writes into `AGENTS.md` during `next dev`, unless you set `agentRules` in `next.config`.

`frogbot help`, `frogbot --help` and `frogbot -h` print the list of commands.

## Run in the background

```bash
frogbot up
# [frogbot] /Users/me/crm is up at http://127.0.0.1:9696
# [frogbot] log: /Users/me/crm/.frogbot/service.log
```

`frogbot up` builds the app for production and keeps it running after the terminal closes, so it stays up while you or a coding agent edit it. It waits until the app answers, prints its URL and log, and exits `0`. If the first build or start fails, it prints the error, leaves nothing running, and exits `1`. Run it again in a folder that is already up and it prints the same URL.

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `--port <n\|auto>` | number or `auto` | the app's last port, else the first free one from `9696` | Serve on this port from now on. See [Port](#port). |
| `--autostart` | flag | off | macOS only: also start the app at login (see below). Elsewhere it exits `1`, and on an app already up without it, it exits `1` and tells you to run `down` first. |

The app listens on `127.0.0.1` and `::1`, so `localhost` reaches it whichever address it resolves to; it isn't reachable from other computers. Each app gets its own port, so several apps run side by side:

```bash
frogbot status
# FOLDER          URL                    STATE          UPTIME  LAST ERROR
# /Users/me/crm   http://127.0.0.1:9696  running        2h 5m
# /Users/me/hr    http://127.0.0.1:9697  update failed  12m     build failed (exit 1): src/hr.ts(3,7): error TS2322: Type 'number' is not assignable to type 'string'.
```

`frogbot status` works from any folder. The states are `starting`, `running`, `building` (an update is on its way; the current version still serves), `update failed` (the last edit didn't build or start; the previous version still serves), `crashed` (restarting) and `stopped`. `LAST ERROR` is the line of the failed step's output that says why: a TypeScript error, else the thrown error, else its last meaningful line; the log has the full output. `frogbot down` stops the app in the current folder, or in the folder you name, and removes its builds; on an app that isn't up it prints `not running` and exits `0`.

### Port

The first `up` picks the first free port from `9696`, and later ones keep it while it stays free. `frogbot up --port 4000` picks the port yourself: FrogBot remembers it in `.frogbot/port` and every later `up` uses it. If something else holds it, `up` exits `1` and names the process, for example `port 4000 is taken by node (pid 123); pick another with --port`, instead of moving the app. `frogbot up --port auto` goes back to picking.

On an app that is already up, `frogbot up --port 4000` moves it to the new port without a rebuild and prints `moved … to http://127.0.0.1:4000`. A port below 1024 needs admin rights, and `up` says so.

### Processes

`up` starts one background supervisor per app, which holds the port and starts each build, schema sync and server. Every one of them stops when the supervisor stops, even when it is killed with `SIGKILL` or crashes, so an app never leaves a server running beside the next `up`. If an older FrogBot left one, the next `up` or `down` stops it, and `status` shows `stopped (server left running, pid N)` until then.

### Updates

While it runs, `up` watches `src/`, `public/`, `frogbot.config.*`, `next.config.*`, `tsconfig.json`, `package.json`, the lockfile and `.env*`. 1.5 seconds after the last change it builds the new version beside the one serving, starts it, and switches traffic over once it answers; requests already open, such as a streaming chat reply, finish on the old version (up to 30 seconds). Changes made during a build start one more build when it ends. A new version goes live only once `/` and `/admin` answer below 500, `/api/health` answers 200 (skipped when the app has no health route) and a request through the API, `/api/access`, answers below 500. A build or start that fails any of these keeps the old version serving.

Builds go in `.frogbot/builds/a` and `.frogbot/builds/b`, which take turns. Each build type-checks with its own generated `.frogbot/builds/<a|b>.tsconfig.json`, which extends your `tsconfig.json` and includes only that build's route types, so deleting a route never breaks the next update. Apps made with FrogBot 0.39 list both build folders in `tsconfig.json`'s `include`; remove those four `.frogbot/builds/…` lines, or `tsc` still reads the old routes, and the log reminds you once per start.

A server that crashes restarts on the same build after 1 second, waiting twice as long after each crash up to 30 seconds, and back to 1 second once it has stayed up for a minute.

### Database schema

With SQLite and no `prodMigrations`, each update brings the database's schema up to the new code before the new version starts, with the same rule as `frogbot dev` (see [Prototyping in development mode](/database/sqlite#prototyping-in-development-mode)): it adds tables, columns and indexes, adds a new required field as a nullable column so existing rows keep working, and keeps removed fields and collections (their data stays, hidden, until you add them back). It never deletes data and never asks: when a change would drop a table, a column or rows, or change a field's type while it holds values the new type can't read (text that isn't a number, for a `number` field), the update stops as `update failed` and the old version keeps serving. Nothing is written to `payload_migrations`, so you can still adopt [migrations](/database/migrations) later. With `prodMigrations` set, the update runs your migrations on connect instead, as `frogbot start` does.

### Log

`.frogbot/service.log` holds timestamped lines from the supervisor, each build, the schema sync and the server, without colour codes. The schema sync logs how many statements it applied, and one line naming the removed fields and collections it keeps hidden, again only when that list changes. The supervisor logs `server back up (pid N)` after a crashed server answers again. Once the file reaches 10 MB it moves to `service.log.1` and a new one starts.

### Start at login

```bash
frogbot up --autostart
```

On macOS, `--autostart` installs `~/Library/LaunchAgents/ai.frogbot.<id>.plist`, which starts the app at login and restarts it if it fails; `frogbot down` removes it. The LaunchAgent runs your app's `node_modules/frogbot/bin.js` with the absolute path of `node`, so reinstalling or upgrading FrogBot keeps it working; after upgrading Node, run `frogbot down` and `frogbot up --autostart` again.

## Generate piece types

```bash
frogbot generate:piece-types src/index.ts --export createResend --output src/piece-types.ts
```

Loads a piece factory and writes the TypeScript input/output types for its actions and triggers, formatted with Prettier.

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `<module>` | file path | Required | Module that exports the piece factory, resolved from the current directory. |
| `--export` | export name | Required | Name of the piece factory export, such as `createResend`. |
| `--output` | file path | Required | File to write (left untouched when content is unchanged). |
| `--check` | flag | off | Exits with `Piece types are stale` instead of writing when out of date (for CI). |

## Port a piece

```bash
frogbot pieces:port google-sheets
```

Contributor command run from the root of the FrogBot repository. Moves `packages/pieces/piece-<slug>` and `test/unit/piece-<slug>` to `.legacy` folders, then scaffolds a native piece package and test skeleton.

| Argument | Type | Default | Description |
| --- | --- | --- | --- |
| `<slug>` | lowercase letters, numbers, and single dashes | Required | Piece slug, such as `google-sheets`. |
