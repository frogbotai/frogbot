Collection search ranks records of one collection by text relevance, vector similarity, or both. You declare named indexes on the collection and query them with `frogbot.search()`, REST, or GraphQL. Ranking runs in the database.

The [Postgres and Vercel Postgres](/database/postgres#collection-search) and [SQLite](/database/sqlite#collection-search) adapters implement search, and every option on this page works the same way on each. Adapter pages list engine-specific details such as supported metrics and languages. On other adapters, any configured search index fails database initialization with `SearchCapabilityError` and reason `not-implemented`; leave `search` off those collections and use [vector fields](/fields/vector) for storage only.

## Configure indexes

Each key under `search` names an index and selects the fields it ranks:

```ts
import type { CollectionConfig } from 'frogbot';

export const Articles: CollectionConfig = {
  slug: 'articles',
  fields: [
    { name: 'title', type: 'text', required: true },
    { name: 'body', type: 'textarea' },
    { name: 'embedding', type: 'vector', dimensions: 1536 },
  ],
  search: {
    content: {
      lexical: { fields: ['title', 'body'] },
      vector: { field: 'embedding' },
    },
    titles: {
      lexical: { fields: ['title'] },
    },
  },
};
```

`dimensions` belongs to the vector field, not the index. When an index includes both components, supplying both query inputs selects hybrid mode with configured reciprocal-rank fusion (`rrf`). FrogBot does not calculate embeddings; your application supplies stored vectors and query vectors. The adapter creates any native indexes as part of the database schema.

### Index options

| Option               | Default                     | Meaning                                                                                                   |
| -------------------- | --------------------------- | --------------------------------------------------------------------------------------------------------- |
| `lexical.fields`     |                             | Text and textarea fields to rank by text relevance.                                                       |
| `lexical.language`   | `'simple'`                  | Stemming and tokenizing language. Each adapter lists the languages it supports.                            |
| `vector.field`       |                             | The vector field to rank by similarity.                                                                    |
| `vector.metric`      | `'cosine'`                  | `cosine`, `euclidean`, or `dotProduct`.                                                                    |
| `vector.approximate` | `true`                      | Build an approximate nearest-neighbour index for this field. Set `false` to always search exactly.          |
| `hybrid.fusion`      | `'rrf'`                     | Reciprocal rank fusion. It is the only method.                                                             |
| `hybrid.weights`     | `{ lexical: 1, vector: 1 }` | Positive multipliers for each component's contribution to the fused score.                                 |
| `defaultCandidates`  | `100`                       | The [candidate count](#candidates) when the query does not set `candidates`. Only indexes with `vector` accept it. |
| `filters`            | every eligible field        | `{ fields }` or `{ exclude }` to choose which stored fields `where` may filter on.                          |

An index with both `lexical` and `vector` accepts a `hybrid` object:

```ts
import type { CollectionConfig } from 'frogbot';

export const Articles: CollectionConfig = {
  slug: 'articles',
  fields: [
    { name: 'title', type: 'text', required: true },
    { name: 'embedding', type: 'vector', dimensions: 1536 },
  ],
  search: {
    content: {
      lexical: { fields: ['title'] },
      vector: { field: 'embedding' },
      hybrid: { weights: { lexical: 1, vector: 2 } },
      defaultCandidates: 200,
    },
  },
};
```

## Query

The operation accepts `collection`, a named `index`, and `query` (`SearchOptions`). The query inputs select the mode:

```ts
import type { FrogBotRequest } from 'frogbot';

export async function searchArticles(req: FrogBotRequest, vector: number[]) {
  const lexical = await req.frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { text: 'account recovery' },
    where: { title: { equals: 'Account recovery' } },
    limit: 10,
    select: { title: true },
    req,
  });

  const semantic = await req.frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { vector },
    req,
  });

  const hybrid = await req.frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { text: 'account recovery', vector },
    req,
  });

  return { lexical, semantic, hybrid };
}
```

Search defaults to enforcing access and requires `req` unless you explicitly set `overrideAccess: true`. That default differs from ordinary Local API CRUD. `index` is currently typed as a string; index names are checked against the collection at runtime. The `vector` must match the indexed field's dimensions and contain finite numbers. A text query must be non-empty, and `limit` defaults to 10 (positive integer required). `where`, `select`, `depth` (defaults to `0`), `candidates`, `draft`, `locale`, and `fallbackLocale` are options, but which filters and modes can run depends on the adapter and selected index.

The database ranks only documents the caller can read: collection read access and your `where` filter are applied before ranking. FrogBot then reads the ranked documents in one ordinary collection read, so collection and field read hooks run on each result as they do for any other read. A ranked document that this read does not return, for example because it was deleted or is no longer readable, is left out; `hits` can therefore be shorter than `limit`. Field-level read access on a ranked or filtered field stops the query with `SearchFilterUnsupportedError` while access is enforced, because scores computed over a hidden value would reveal it.

The result is `{ mode, ranking, hits }`: `mode` is `lexical`, `vector`, or `hybrid`; `ranking` contains `method`, `higherIsBetter`, and `approximate`; each hit has `{ doc, score }`, in ranked order. Hybrid results add component details, described below. Scores are ordering values, not probabilities; scores from different methods are not directly comparable. An empty `hits` array is a successful no-match result. Ranking and hybrid fusion run in the database, with no JavaScript similarity or fusion fallback.

### Candidates

`candidates` sets how many top matches a ranked component considers before `limit` is applied. It has one meaning on every adapter and applies to vector and hybrid queries:

- **Approximate vector search** asks the nearest-neighbour index for this many neighbours. A larger value finds more true neighbours, and leaves more hits after your filters on adapters whose index cannot filter, at the cost of a slower query.
- **Hybrid search** takes this many top matches from the lexical and vector components separately, then fuses them. A document outside both candidate lists cannot appear in the results, so a larger value can surface documents that rank moderately in both components.

Lexical queries and exact vector queries rank every matching document and ignore it. Each adapter page describes how its engine uses the count.

The count comes from the query's `candidates`, then the index's `defaultCandidates`, then `100`, and is never lower than `limit`:

```ts
import type { FrogBotRequest } from 'frogbot';

export async function deepSearch(req: FrogBotRequest, vector: number[]) {
  return req.frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { text: 'account recovery', vector },
    limit: 10,
    candidates: 500,
    req,
  });
}
```

`candidates` must be a positive integer.

### Hybrid components

Each hybrid hit also has `components`, the rank and score the document received from each component before fusion. A component the document did not match is `null`:

```ts
const hit = {
  doc: { id: 12, title: 'Account recovery' },
  score: 0.0325,
  components: {
    lexical: { rank: 1, score: 0.1 },
    vector: { rank: 3, score: 0.92 },
  },
};
```

Component scores use the same scale as a lexical-only or vector-only search on the same index. `ranking.components` describes each one with `method`, `higherIsBetter`, and `approximate`, so you can, for example, drop hits whose vector similarity is below a threshold. Lexical and vector results do not include `components`.

## REST API

Every collection with a search index gets a `POST /api/{collection-slug}/search` endpoint. The JSON body accepts the same options as `frogbot.search()` except `collection`, `overrideAccess`, and `req`: the endpoint always searches as the requesting user with access enforced.

```ts
const response = await fetch('/api/articles/search', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  credentials: 'include',
  body: JSON.stringify({
    index: 'content',
    query: { text: 'account recovery' },
    where: { title: { equals: 'Account recovery' } },
    limit: 5,
  }),
});

const { mode, ranking, hits } = await response.json();
```

The response body is the same `{ mode, ranking, hits }` object that `frogbot.search()` returns. See the [REST API](/rest-api/overview) for authentication.

## GraphQL

Every searchable collection with GraphQL queries enabled also gets a `search` query named after its plural GraphQL name, such as `searchArticles`. Setting the collection's `graphQL` option to `false` or `graphQL.disableQueries` to `true` omits it.

```graphql
query {
  searchArticles(index: "content", text: "account recovery", limit: 5) {
    mode
    ranking {
      method
      higherIsBetter
      approximate
    }
    hits {
      score
      doc {
        id
        title
      }
    }
  }
}
```

Hybrid hits expose `components { lexical { rank score } vector { rank score } }`, and `ranking` exposes `components { lexical { method higherIsBetter approximate } vector { ... } }`. Both are `null` for lexical and vector queries.

The query accepts `index`, `text`, `vector`, `where`, `limit`, `candidates`, `draft`, and, when localization is enabled, `locale` and `fallbackLocale`. `doc` uses the collection's GraphQL type. Like the REST endpoint, the query always enforces the requesting user's access. See the [GraphQL API](/graphql/overview).

## Setup and errors

FrogBot checks every configured index when the database initializes, including when you create or run migrations. The check is silent when a configured index is compatible. On an adapter without search, **any configured index fails initialization** with `SearchCapabilityError` (`reason: 'not-implemented'`), naming the collection, index, and mode. An adapter also stops setup when the engine cannot run an option (`engine-gap`) or a database prerequisite is missing; see the [Postgres](/database/postgres#prerequisites) and [SQLite](/database/sqlite#prerequisites) prerequisites.

The core also exports `SearchValidationError`, `SearchFilterUnsupportedError`, and `SearchReadinessError` for invalid inputs, unsupported filters or visibility rules, and invalid or unready ranked results. REST and GraphQL report them with these HTTP statuses:

| Error                          | Status | Meaning                                                             |
| ------------------------------ | ------ | ------------------------------------------------------------------- |
| `SearchValidationError`        | `400`  | The index, query, or an option is invalid.                          |
| `SearchFilterUnsupportedError` | `400`  | A filter, locale, or field visibility rule cannot be searched.      |
| `SearchCapabilityError`        | `501`  | The database adapter cannot run the requested mode.                 |
| `SearchReadinessError`         | `503`  | The native index is not ready or returned an invalid ranked result. |

A caller without collection read access receives `403`. `SearchCapabilityError` carries a `reason`: `not-implemented`, `engine-gap`, `missing-prerequisite`, `permission-denied`, or `setup-failed`. See the [database status](/database/overview#collection-search-status) for adapter support.

## Adapter integration

Database adapters add search through a `search` object on the adapter. `capabilities` declares which modes an index supports. `buildSchema` receives every collection's normalized indexes while the database initializes, before tables and indexes are created, so native search indexes are part of schema push and migrations. `readiness` can reject a query while an index is still building, and `search` returns ranked `{ id, score }` rows for FrogBot to read back. The Postgres and SQLite adapters implement this contract. `search` receives the resolved `candidates` count for vector and hybrid queries.

You can optionally call the existing `frogbot.rerank()` on readable hits, or compose retrieval and answer generation in your own application. There is no automatic embedding or built-in RAG preset for this collection search API. The separate [search plugin](/plugins/search) has its own contract.
