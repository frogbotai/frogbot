Collection search ranks the records of one collection by text relevance, vector similarity, or both. You declare named indexes on the collection, then query them. Ranking runs in the database.

| To | Use |
| --- | --- |
| Search one collection from server code | [`frogbot.search()`](#query) |
| Search several collections in one call | [`frogbot.searchMany()`](#search-several-collections) |
| Search over HTTP | The [REST](#rest-api) endpoints or the [GraphQL](#graphql) queries |
| Let an agent search | [`searchTool()`](#search-from-an-agent) |

## Database support

| Adapter | Lexical | Vector | Hybrid |
| --- | --- | --- | --- |
| [Postgres and Vercel Postgres](/database/postgres#collection-search) | Yes | Yes | Yes |
| [SQLite](/database/sqlite#collection-search) | Yes | Yes | Yes |
| [MongoDB](/database/mongodb#collection-search) | Yes | Yes | Yes |
| [Cloudflare D1](/database/sqlite#d1-collection-search) | Yes | No | No |

Every option on this page works the same way on Postgres, SQLite, and MongoDB. Each adapter page lists engine-specific details, such as the metrics and languages it supports.

- **Cloudflare D1** has no native vector search. An index with `vector` fails setup with `SearchCapabilityError` and reason `engine-gap`.
- **Any other adapter** fails database initialization with `SearchCapabilityError` and reason `not-implemented` when a collection configures a search index. Leave `search` off those collections and use [vector fields](/fields/vector) for storage only.

## Configure indexes

Each key under `search` names an index and selects the fields it ranks:

```ts
import type { CollectionConfig } from 'frogbot';

export const Articles: CollectionConfig = {
  slug: 'articles',
  fields: [
    { name: 'title', type: 'text', required: true },
    { name: 'body', type: 'textarea' },
    { name: 'embedding', type: 'vector', dimensions: 1536 },
  ],
  search: {
    content: {
      lexical: { fields: ['title', 'body'] },
      vector: { field: 'embedding' },
    },
    titles: {
      lexical: { fields: ['title'] },
    },
  },
};
```

- **`dimensions` belongs to the vector field**, not the index.
- **An index with both `lexical` and `vector` supports hybrid search.** A query that supplies both text and a vector runs in hybrid mode, which combines the two rankings with the configured reciprocal rank fusion (`rrf`).
- **Your application supplies query vectors.** Stored vectors come from your application too, or from [`embedFrom`](/fields/vector#embed-on-save), which fills a vector field from the record's text on save.
- **The adapter creates the native indexes** as part of the database schema.

### Index options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `lexical.fields` | `string[]` | Required with `lexical` | Text and textarea fields to rank by text relevance. |
| `lexical.language` | `string` | `'simple'` | Stemming and tokenizing language. Each adapter lists the languages it supports. |
| `vector.field` | `string` | Required with `vector` | The vector field to rank by similarity. |
| `vector.metric` | `'cosine' \| 'euclidean' \| 'dotProduct'` | `'cosine'` | Similarity metric. |
| `vector.approximate` | `boolean` | `true` | Build an approximate nearest-neighbour index for this field. Set `false` to always search exactly. |
| `hybrid.fusion` | `'rrf'` | `'rrf'` | Reciprocal rank fusion. It is the only method. |
| `hybrid.weights` | `{ lexical: number; vector: number }` | `{ lexical: 1, vector: 1 }` | Positive multipliers for each component's contribution to the fused score. |
| `defaultCandidates` | `number` | `100` | The [candidate count](#candidates) when the query does not set `candidates`. Only indexes with `vector` accept it. |
| `filters` | `{ fields: string[] } \| { exclude: string[] }` | Every eligible field | Which stored fields `where` may filter on: only `fields`, or every eligible field except `exclude`. |

An index with both `lexical` and `vector` accepts a `hybrid` object:

```ts
import type { CollectionConfig } from 'frogbot';

export const Articles: CollectionConfig = {
  slug: 'articles',
  fields: [
    { name: 'title', type: 'text', required: true },
    { name: 'embedding', type: 'vector', dimensions: 1536 },
  ],
  search: {
    content: {
      lexical: { fields: ['title'] },
      vector: { field: 'embedding' },
      hybrid: { weights: { lexical: 1, vector: 2 } },
      defaultCandidates: 200,
    },
  },
};
```

## Query

`frogbot.search()` takes a `collection`, the name of an `index`, and a `query`. The inputs in `query` select the mode:

| `query` | Mode | The index needs |
| --- | --- | --- |
| `{ text }` | `lexical` | `lexical` |
| `{ vector }` | `vector` | `vector` |
| `{ text, vector }` | `hybrid` | `lexical` and `vector` |

```ts
import type { FrogBotRequest } from 'frogbot';

export async function searchArticles(req: FrogBotRequest, vector: number[]) {
  const lexical = await req.frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { text: 'account recovery' },
    where: { title: { equals: 'Account recovery' } },
    limit: 10,
    select: { title: true },
    req,
  });

  const semantic = await req.frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { vector },
    req,
  });

  const hybrid = await req.frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { text: 'account recovery', vector },
    req,
  });

  return { lexical, semantic, hybrid };
}
```

### Search options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `collection` | `CollectionSlug` | Required | Collection to search. |
| `index` | `string` | Required | Name of an index under the collection's `search`. The type is `string`, so TypeScript does not check the name. FrogBot checks it against the collection when the query runs. |
| `query` | `{ text?: string; vector?: number[] }` | Required | `text` alone runs lexical search, `vector` alone runs vector search, and both run hybrid search. The index must have the matching components. |
| `where` | `Where` | — | Filter applied before ranking. Only fields allowed by the index's `filters` can be used. |
| `limit` | `number` | `10` | Maximum hits. Must be a positive integer. |
| `candidates` | `number` | The index's `defaultCandidates`, then `100` | See [Candidates](#candidates). Must be a positive integer. |
| `select` | `SelectType` | Every field | Fields to return on each `doc`. |
| `depth` | `number` | `0` | Relationship depth for each `doc`. Must be a non-negative integer. |
| `draft` | `boolean` | `false` | Search and return draft versions. |
| `locale` | `string` | The request locale | Locale to search and return. `'all'` is rejected because each hit needs one locale. |
| `fallbackLocale` | `string \| false` | The request fallback | Locale used for missing localized values, or `false` for none. |
| `overrideAccess` | `boolean` | `false` | Set `true` to skip collection and field read access. Required when `req` is omitted. |
| `req` | `FrogBotRequest` | Required unless `overrideAccess: true` | Request whose user's access is enforced. |

FrogBot validates the query before it runs. Each of these fails with `SearchValidationError`:

- The `index` is not configured on the collection, or it lacks the component that the mode needs.
- `query` has neither `text` nor `vector`, or `query.text` is empty.
- `query.vector` does not have the indexed field's `dimensions`, or it contains a value that is not a finite number.
- `limit` or `candidates` is not a positive integer, or `depth` is not a non-negative integer.

Which filters and modes can run also depends on the adapter and the selected index.

### Access

<Warning>
Search enforces access by default. `overrideAccess` defaults to `false`, and a call without `req` fails with `SearchValidationError`. Pass the request when you act for a user. Set `overrideAccess: true` only for trusted server work, such as a script or a job.
</Warning>

```ts
import type { FrogBot, FrogBotRequest } from 'frogbot';

// Acting for a user: pass the request, and search runs with that user's access.
export async function searchAsUser(req: FrogBotRequest, text: string) {
  return req.frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { text },
    req,
  });
}

// Trusted server work: skip access explicitly.
export async function searchAsServer(frogbot: FrogBot, text: string) {
  return frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { text },
    overrideAccess: true,
  });
}
```

A query runs in two steps:

1. **The database ranks.** It ranks only documents that the caller can read, because it applies collection read access and your `where` filter before ranking.
2. **FrogBot reads the ranked documents** in one ordinary collection read. Collection and field read hooks run on each result, as they do for any other read.

Two consequences follow:

- **`hits` can be shorter than `limit`.** A ranked document that the read does not return is left out, for example because it was deleted or is no longer readable.
- **A field with its own read access can't be ranked or filtered.** While access is enforced, field-level read access on a ranked or filtered field stops the query with `SearchFilterUnsupportedError`, because scores computed over a hidden value would reveal it.

### Results

`frogbot.search()` returns `{ mode, ranking, hits }`:

| Field | Type | Description |
| --- | --- | --- |
| `mode` | `'lexical' \| 'vector' \| 'hybrid'` | The mode that the query inputs selected. |
| `ranking` | `{ method, higherIsBetter, approximate, components? }` | How the index ranked: the ranking method, whether a higher score is a better match, and whether the ranking was approximate. |
| `hits` | `{ doc, score, components? }[]` | The matching documents and their scores, in ranked order. |

Hybrid results add `components` to `ranking` and to each hit. See [Hybrid components](#hybrid-components).

- **Scores order the hits. They are not probabilities.** Scores from different methods are not directly comparable, and neither are [scores from different collections](#scores-across-collections).
- **No match is a success.** The result has an empty `hits` array.
- **Results hold only the top hits.** There are no totals, pages, or cursors.
- **The database does the ranking.** Ranking and hybrid fusion run in the database, with no JavaScript similarity or fusion fallback.

### Candidates

`candidates` sets how many top matches a ranked component considers before `limit` is applied. It has one meaning on every adapter:

| Query | What `candidates` does |
| --- | --- |
| Approximate vector | Asks the nearest-neighbour index for this many neighbours. A larger value finds more true neighbours, and it leaves more hits after your filters on adapters whose index cannot filter. The query is slower. |
| Hybrid | Takes this many top matches from the lexical component and from the vector component, then fuses them. A document outside both candidate lists cannot appear in the results, so a larger value can surface documents that rank moderately in both components. |
| Lexical, or exact vector | Nothing. These queries rank every matching document. |

Each adapter page describes how its engine uses the count.

The count comes from the query's `candidates`, then the index's `defaultCandidates`, then `100`. It is never lower than `limit`, and it must be a positive integer.

```ts
import type { FrogBotRequest } from 'frogbot';

export async function deepSearch(req: FrogBotRequest, vector: number[]) {
  return req.frogbot.search({
    collection: 'articles',
    index: 'content',
    query: { text: 'account recovery', vector },
    limit: 10,
    candidates: 500,
    req,
  });
}
```

### Hybrid components

Each hybrid hit also has `components`, the rank and score the document received from each component before fusion. A component the document did not match is `null`:

```ts
const hit = {
  doc: { id: 12, title: 'Account recovery' },
  score: 0.0325,
  components: {
    lexical: { rank: 1, score: 0.1 },
    vector: { rank: 3, score: 0.92 },
  },
};
```

- **Component scores use the same scale** as a lexical-only or vector-only search on the same index.
- **`ranking.components` describes each component** with `method`, `higherIsBetter`, and `approximate`. You can use it, for example, to drop hits whose vector similarity is below a threshold.
- **Lexical and vector results do not include `components`.**

## Search from an agent

`searchTool()` turns one index into a tool an [agent](/agents/overview#add-tools) can call. The model sends a search phrase and gets back the best matches:

```ts
import { buildConfig } from 'frogbot'
import { searchTool } from 'frogbot/tools'

export default buildConfig({
  agents: [
    {
      slug: 'support',
      model: 'fast',
      instructions: 'Answer from the help center. Search it before you answer.',
      tools: [
        searchTool({
          collection: 'articles',
          index: 'content',
          select: { title: true, body: true },
          model: 'openai/text-embedding-3-small',
          where: { status: { equals: 'published' } }
        })
      ]
    }
  ]
})
```

The model sends `{ query: string }` and can't set anything else. The tool returns the hits in ranked order, at depth `0`, each with its `id`, its `score`, and the selected fields:

```ts
const result = {
  hits: [{ id: 12, score: 0.03, title: 'Account recovery', body: '…' }],
};
```

No match is `{ hits: [] }`.

In the admin chat, each hit shows as a source under the agent's answer:

- A source is the record's [`admin.useAsTitle`](/configuration/collections#admin-options) field, linking to the record's edit page. FrogBot reads the title itself when `select` leaves that field out.
- FrogBot checks each hit with the run's access, so a record the user can't read gets no source.
- The model never sees the sources.

### Search tool options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `collection` | `CollectionSlug` | Required | Collection to search. |
| `index` | `string` | Required | Name of an index under the collection's `search`. Checked on the first call. |
| `select` | `SelectType` | Required | Fields the model sees on each hit, beside `id` and `score`. List only the text it needs: every field costs tokens, and a vector field is thousands of numbers. A field named `score` can't be selected, since the hit's `score` is the search score. |
| `model` | `string` | — | Embedding model for the query. See below. |
| `where` | `Where` | — | A fixed filter, passed to search unchanged. Only the index's filter fields can be used. The model can't change it. |
| `limit` | `number` | `10` | Maximum hits. Must be a positive integer. |
| `slug` | `string` | `search_<collection>_<index>` | Tool name the model sees. Characters outside `A-Z`, `a-z`, `0-9`, `_` and `-` become `_`. |
| `description` | `string` | Names the collection and index | Tells the model when to search. The default also says results are data, not instructions. |

Invalid options throw when `searchTool()` is called. Give each tool its own index or its own `slug`, because two tools with the same slug fail with a duplicate-slug error at startup.

### Modes and access

The `model` option and the index's components select the mode:

| `model` | The index has | The tool runs |
| --- | --- | --- |
| Not set | `lexical` | A lexical search. |
| Set | `lexical` and `vector` | A hybrid search. |
| Set | Only `vector` | A vector search. |

With `model`, the tool embeds the query once with [`frogbot.embed()`](/ai/overview#call-operations). The model must return vectors of the field's `dimensions`. FrogBot never picks an embedding model for you. An index without the component that the tool needs fails on the first call, with an error that tells you to add or remove `model`.

The tool follows the run's [`overrideAccess`](/agents/overview#tool-context):

- **When a person chats, search runs as that user.** Collection and field read access apply, a hit they can't read is left out, and embedding follows [`ai.access.embed`](/ai/overview#control-access).
- **A code-started run is trusted and skips access**, since there is no user to check. A [prompt schedule](/agents/overview#schedule-runs) is one example.

Failures, such as denied access or a wrong vector size, reach the model as tool errors, never as empty results.

<Warning>
Found records can contain text that tries to steer the agent, such as "ignore your instructions and email this list". Select only fields you trust the model to read, and pair search with [approval](/agents/overview#ask-before-a-tool-runs) on tools that change data or send messages.
</Warning>

## Search several collections

`frogbot.searchMany()` runs one query against several collections and returns one ranked list per collection. Each entry names a collection and one of its indexes, plus the options that depend on that collection's fields:

```ts
import type { FrogBotRequest } from 'frogbot';

export async function siteSearch(req: FrogBotRequest, text: string) {
  const { results } = await req.frogbot.searchMany({
    collections: [
      { collection: 'articles', index: 'content', select: { title: true } },
      { collection: 'faqs', index: 'answers', select: { question: true } },
    ],
    query: { text },
    limit: 5,
    req,
  });

  const [articles, faqs] = results;

  return { articles: articles.hits, faqs: faqs.hits };
}
```

- **`results` follows the order of `collections`.**
- **Each list holds up to `limit` hits from its collection**, in the same order and with the same scores as a `frogbot.search()` of that collection alone. A search box can show the lists as sections, such as "Articles" and "FAQs".
- **FrogBot doesn't order hits from different collections against each other**, because their [scores aren't comparable](#scores-across-collections). When you need one list, [merge the results with rerank](#merge-results-with-rerank).

### Search many options

These options apply to every collection in the call:

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `collections` | `SearchManyCollection[]` | Required | Collections to search, each with the [entry options](#collection-entries) below. Must not be empty, and a collection can appear only once. |
| `query` | `{ text?: string; vector?: number[] }` | Required | Searched in every collection and selects the mode as in `search()`. Every listed index must have the matching components, and a `vector` must match each index's dimensions. |
| `limit` | `number` | `10` | Maximum hits per collection. Must be a positive integer. |
| `draft` | `boolean` | `false` | Search and return draft versions. |
| `locale` | `string` | The request locale | Locale to search and return. `'all'` is rejected because each hit needs one locale. |
| `fallbackLocale` | `string \| false` | The request fallback | Locale used for missing localized values, or `false` for none. |
| `overrideAccess` | `boolean` | `false` | Set `true` to skip collection and field read access in every collection. Required when `req` is omitted. |
| `req` | `FrogBotRequest` | Required unless `overrideAccess: true` | Request whose user's access is enforced in every collection. |

#### Collection entries

Each entry in `collections` accepts:

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `collection` | `CollectionSlug` | Required | Collection to search. |
| `index` | `string` | Required | Name of an index under this collection's `search`. FrogBot checks it when the query runs. |
| `where` | `Where` | — | Filter applied before ranking. Only fields allowed by this index's `filters` can be used. |
| `select` | `SelectType` | Every field | Fields to return on each `doc`. |
| `candidates` | `number` | The index's `defaultCandidates`, then `100` | See [Candidates](#candidates). Must be a positive integer. |
| `depth` | `number` | `0` | Relationship depth for each `doc`. Must be a non-negative integer. |

Any other key on an entry, such as its own `query` or `limit`, fails with `SearchValidationError`.

### Search many results

The result is `{ results }`, with one item per entry:

| Field | Type | Description |
| --- | --- | --- |
| `collection` | `CollectionSlug` | The entry's collection. |
| `mode` | `'lexical' \| 'vector' \| 'hybrid'` | The mode selected by the shared query, the same for every item. |
| `ranking` | `{ method, higherIsBetter, approximate, components? }` | How this collection's index ranked, as in a single search. It can differ between collections, for example when one index is approximate and another is exact. |
| `hits` | `{ doc, score, components? }[]` | This collection's ranked hits, as in a single search. Can be empty or shorter than `limit`. |

Each item is typed by its collection. In the example above, `articles.hits[0].doc` is an article and `faqs.hits[0].doc` is a FAQ. When you loop over `results`, checking `item.collection` narrows the document type.

### Failures

The call succeeds or fails as a whole.

**Before any query runs,** FrogBot checks the list and every entry. Each of these fails with `SearchValidationError`:

- The list is empty.
- An entry isn't an object, or it lacks `collection` or `index`.
- An entry has an unknown key.
- A collection appears more than once.
- An index isn't configured, or it lacks the component that the query's mode needs.
- A vector has the wrong length.
- An option is invalid.

`locale: 'all'` fails with `SearchFilterUnsupportedError`, also with status `400`.

**FrogBot then searches the collections one after another,** in list order, on the same request, so the call also works inside a database transaction.

- If any collection fails, the whole call fails and returns no results.
- A collection the user can't read fails the call with `403`, as a single search of it would. It is not left out.
- Errors about one entry's index, query, options, or filters name its collection and index, for example `Search index 'answers' in collection 'faqs' requires a vector of 768 finite numbers.`

### Scores across collections

Within one collection, a hit ranked higher is a better match. Across collections the scores don't line up:

- **Text scores are relative to each collection.** On SQLite, D1, and MongoDB, BM25 weighs each word by how rare it is in that collection's records, so the same word scores differently in 40 FAQs than in 8,000 articles. On every adapter, the score also depends on which fields and language the index ranks.
- **Vector scores depend on each index's metric.** Cosine and dot product are similarities where higher is better. Euclidean is a distance where lower is better. Two vector fields with the same dimensions can still hold embeddings from different models. FrogBot doesn't record which model produced a vector, so it can't tell whether two similarities are comparable.
- **Hybrid scores come from rank positions.** Reciprocal rank fusion scores a document by where it ranked within its own collection, so comparing fused scores across collections compares positions, not how well each document matched.

### Merge results with rerank

To get one list, for example to choose passages for an AI answer, merge the lists and order them with [`frogbot.rerank()`](/ai/overview#rerank-options). It scores each text against the query with your rerank model, so the scores are comparable regardless of which collection a hit came from:

```ts
import type { FrogBotRequest } from 'frogbot';

export async function retrieve(req: FrogBotRequest, question: string) {
  const { results } = await req.frogbot.searchMany({
    collections: [
      { collection: 'articles', index: 'content' },
      { collection: 'faqs', index: 'answers' },
    ],
    query: { text: question },
    limit: 20,
    req,
  });

  const [articles, faqs] = results;

  const passages = [
    ...articles.hits.map(({ doc }) => ({
      collection: 'articles',
      id: doc.id,
      text: `${doc.title}\n${doc.body ?? ''}`,
    })),
    ...faqs.hits.map(({ doc }) => ({
      collection: 'faqs',
      id: doc.id,
      text: `${doc.question}\n${doc.answer}`,
    })),
  ];

  const { ranking } = await req.frogbot.rerank({
    model: 'voyage/rerank-2.5',
    query: question,
    documents: passages.map(({ text }) => text),
    topN: 5,
    req,
  });

  return ranking.map(({ originalIndex, score }) => ({ ...passages[originalIndex], score }));
}
```

`ranking` is sorted by relevance, and `originalIndex` points back into `documents`.

<Note>
Reranking calls a model on every search, which adds cost and delay. It needs a configured rerank model.
</Note>

## REST API

Both endpoints always search as the requesting user, with access enforced. See the [REST API](/rest-api/overview) for authentication, and [Setup and errors](#setup-and-errors) for the error statuses.

| Endpoint | Runs | Exists when |
| --- | --- | --- |
| `POST /api/{collection-slug}/search` | [`frogbot.search()`](#query) | The collection has a search index. |
| `POST /api/frogbot/search` | [`frogbot.searchMany()`](#search-several-collections) | At least one collection has a search index. |

### One collection

The JSON body accepts the same options as `frogbot.search()`, except `collection`, `overrideAccess`, and `req`.

```ts
const response = await fetch('/api/articles/search', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  credentials: 'include',
  body: JSON.stringify({
    index: 'content',
    query: { text: 'account recovery' },
    where: { title: { equals: 'Account recovery' } },
    limit: 5,
  }),
});

const { mode, ranking, hits } = await response.json();
```

The response body is the same `{ mode, ranking, hits }` object that `frogbot.search()` returns. The admin's [Cmd+K palette](/admin/admin-navigation#search-with-cmdk) calls this endpoint to find records.

### Several collections

The JSON body accepts `collections`, `query`, `limit`, `draft`, `locale`, and `fallbackLocale`. Each entry in `collections` accepts the same keys as in `searchMany()`. Any other key fails with `400`, and a collection the user can't read fails the whole request with `403`.

```ts
const response = await fetch('/api/frogbot/search', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  credentials: 'include',
  body: JSON.stringify({
    collections: [
      { collection: 'articles', index: 'content' },
      { collection: 'faqs', index: 'answers' },
    ],
    query: { text: 'reset password' },
    limit: 5,
  }),
});

const { results } = await response.json();
```

The response body is the same `{ results }` object that `frogbot.searchMany()` returns.

## GraphQL

Every searchable collection with GraphQL queries enabled gets a search query named after its plural GraphQL name, such as `searchArticles`. To omit the query, set the collection's `graphQL` option to `false` or `graphQL.disableQueries` to `true`.

```graphql
query {
  searchArticles(index: "content", text: "account recovery", limit: 5) {
    mode
    ranking {
      method
      higherIsBetter
      approximate
    }
    hits {
      score
      doc {
        id
        title
      }
    }
  }
}
```

- **Arguments.** The query accepts `index`, `text`, `vector`, `where`, `limit`, `candidates`, and `draft`. When localization is enabled, it also accepts `locale` and `fallbackLocale`.
- **Access.** Like the REST endpoints, the query always enforces the requesting user's access.
- **Documents.** `doc` uses the collection's GraphQL type.
- **Hybrid components.** Hybrid hits expose `components { lexical { rank score } vector { rank score } }`, and `ranking` exposes `components { lexical { method higherIsBetter approximate } vector { ... } }`. Both are `null` for lexical and vector queries.

See the [GraphQL API](/graphql/overview).

### Several collections in one request

GraphQL has no query that searches several collections. Call each collection's search query in one request instead. Use aliases to name the results and to call the same query more than once:

```graphql
query {
```

## Setup and errors

### Setup checks

FrogBot checks every configured index when the database initializes, including when you create or run migrations. A compatible index passes silently. An incompatible index stops setup with `SearchCapabilityError`:

| Cause | `reason` |
| --- | --- |
| The adapter has no search. Any configured index fails, and the error names the collection, index, and mode. | `not-implemented` |
| The engine cannot run an option. See the [D1 limits](/database/sqlite#d1-collection-search). | `engine-gap` |
| A database prerequisite is missing. See the [Postgres](/database/postgres#prerequisites) and [SQLite](/database/sqlite#prerequisites) prerequisites. | `missing-prerequisite` |

The `reason` can also be `permission-denied` or `setup-failed`. See the [database status](/database/overview#collection-search-status) for adapter support.

### Errors

FrogBot exports four error classes. REST and GraphQL report them with these HTTP statuses:

| Error | Status | Meaning |
| --- | --- | --- |
| `SearchValidationError` | `400` | The index, query, or an option is invalid. |
| `SearchFilterUnsupportedError` | `400` | A filter, locale, or field visibility rule cannot be searched. |
| `SearchCapabilityError` | `501` | The database adapter cannot run the requested mode. It carries the `reason`. |
| `SearchReadinessError` | `503` | The native index is not ready, or it returned an invalid ranked result. |

A caller without collection read access receives `403`.

## Adapter integration

A database adapter adds search through a `search` object on the adapter. The Postgres, SQLite, MongoDB, and D1 adapters implement this contract.

| Member | What it does |
| --- | --- |
| `capabilities` | Declares which modes an index supports. |
| `buildSchema` | Receives every collection's normalized indexes while the database initializes, before tables and indexes are created. Native search indexes are therefore part of schema push and migrations. |
| `readiness` | Can reject a query while an index is still building. |
| `search` | Returns ranked `{ id, score }` rows for FrogBot to read back. For vector and hybrid queries, it receives the resolved `candidates` count. |

## Build retrieval for AI answers

Collection search has no built-in RAG preset. You compose retrieval and answer generation in your own application:

- **Embed the query yourself.** `frogbot.search()` does not embed query text. Pass a vector, for example from [`frogbot.embed()`](/ai/overview#call-operations). [`searchTool()`](#search-from-an-agent) embeds the query for an agent when you set its `model`.
- **Rerank when you need to.** To reorder readable hits with a model, call `frogbot.rerank()`, as in [Merge results with rerank](#merge-results-with-rerank).
