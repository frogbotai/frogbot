Every provider — built-in or self-hosted — lives under the same `providers` key. There is no separate list for custom endpoints.

```ts
import { createGateway } from '@frogbotai/gateway'

const gw = createGateway({
  providers: {
    openai: {},
    'bedrock': {},
    ollama: { baseURL: 'http://localhost:11434/v1' }
  }
})
```

`openai` and `bedrock` are recognized provider names, so they take that provider's typed config. `ollama` isn't a built-in name, so it's treated as a generic OpenAI-compatible endpoint — the key becomes its dispatch prefix (`ollama/llama3.2`).

## Built-in providers

Alibaba, Anthropic, Anthropic (AWS), AssemblyAI, Azure, Baseten, Amazon Bedrock, Black Forest Labs, ByteDance, Cerebras, Cohere, Deepgram, DeepInfra, DeepSeek, ElevenLabs, fal, Fireworks, Gladia, Google, Google Vertex, Groq, Hugging Face, Hume, Kling AI, LMNT, Luma, Mistral, Moonshot AI, OpenAI, OpenRouter, Perplexity, Prodia, Replicate, Together AI, TypeSafe AI, Vercel AI Gateway, Voyage, xAI.

Each ships its own credential shape (`apiKey`, `region`, `accessKeyId`, ...) and its `envVars` list, used for config fallback and CLI env auto-discovery. Bedrock also supports ambient AWS credentials. See [Configuration](/gateway/configuration#auto-discover-from-env) for the full env var reference.

Built-in providers route only models in the catalog. Config also accepts an optional `models` allowlist of unprefixed catalog IDs to narrow that set. The list is enforced after alias canonicalization across HTTP routes and in-process model resolvers. See [Restrict built-in models](/gateway/configuration#restrict-built-in-models).

<Warning>
  Bedrock inference profiles replace the non-invocable bare IDs for Nova 2 Lite,
  Llama 3.1 8B, and Llama 3.3 70B. Replace
  `amazon.nova-2-lite-v1:0` with `global.amazon.nova-2-lite-v1:0`,
  `meta.llama3-1-8b-instruct-v1:0` with `us.meta.llama3-1-8b-instruct-v1:0`,
  and `meta.llama3-3-70b-instruct-v1:0` with
  `us.meta.llama3-3-70b-instruct-v1:0` in model allowlists and requests.
</Warning>

## TypeSafe AI evaluation

TypeSafe AI provides evaluation models for [`POST /v1/evaluate`](/gateway/overview#evaluate-over-http) and [local `frogbot.evaluate()`](/ai/overview#evaluate-state), not chat or embedding models. Set `TYPESAFE_AI_API_KEY` in the server environment and configure `providers: { 'typesafe-ai': {} }` in a standalone gateway, or `ai: { providers: { 'typesafe-ai': true } }` in FrogBot. To use a different server-side secret, set `apiKey` instead:

```ts
ai: {
  providers: {
    'typesafe-ai': { apiKey: process.env.MY_TYPESAFE_KEY }
  }
}
```

The key stays on the server; authenticate callers in your standalone host or through FrogBot's authenticated `/api/v1/evaluate` mount. FrogBot accepts `typesafe-ai/jev` and `typesafe-ai/jev-latest` and sends both to TypeSafe as `jev-latest`. Bare `jev` is not a documented TypeSafe upstream model ID. An optional built-in `models` allowlist uses unprefixed IDs, for example `models: ['jev-latest']`; the alias is canonicalized before checking it.

As of September 23, 2026, TypeSafe lists Jev 1.13 at **$0.042 per million input tokens**, with no charge for output tokens. FrogBot's USD cost uses these catalog rates as an estimate, not a provider invoice. The upstream `jev-latest` alias and its pricing can change; check [TypeSafe's model list](https://docs.typesafe.ai/models.md) for current rates.

## Vercel AI Gateway

The `vercel` provider sends requests to [Vercel AI Gateway](https://vercel.com/docs/ai-gateway), which serves many model creators through one key. Set `AI_GATEWAY_API_KEY` in the server environment and configure `providers: { vercel: {} }` in a standalone gateway, or `ai: { providers: { vercel: true } }` in FrogBot. `AI_GATEWAY_BASE_URL` optionally overrides the endpoint. To use a different secret, set `apiKey` instead.

The key is required. A Vercel deployment's OIDC token does not enable the provider, so a project on Vercel can send its traffic to another provider without AI Gateway turning on.

Model IDs have the form `vercel/<creator>/<model>`, for example `vercel/anthropic/claude-sonnet-4.6` or `vercel/openai/gpt-5.4-mini`. FrogBot accepts the chat models that [models.dev](https://models.dev) lists for Vercel with a price, and uses those prices for usage cost. Other IDs return `model_not_found`. Image, video, speech, transcription, embedding, and rerank models are not available through this provider. Narrow the list with `models`, which uses IDs without the `vercel/` prefix:

```ts
createGateway({
  providers: {
    vercel: { models: ['anthropic/claude-sonnet-4.6', 'openai/gpt-5.4-mini'] }
  }
})
```

For Anthropic, OpenAI, and Google models, reasoning and cache options are translated as they are for the direct provider. For example, chat `reasoning_effort` on a Claude model becomes a thinking budget, and `cache_control` markers become Anthropic cache control.

Pass [AI Gateway routing options](https://vercel.com/docs/ai-gateway/models-and-providers/provider-options) such as `order`, `only`, and `models` in a `gateway` field on `/v1/chat/completions`, or set `providerOptions.gateway` in a [`beforeUpstream` hook](/gateway/hooks). They reach AI Gateway unchanged:

```json
{
  "model": "vercel/anthropic/claude-sonnet-4.6",
  "messages": [{ "role": "user", "content": "Hello" }],
  "gateway": { "order": ["bedrock", "anthropic"] }
}
```

Requests identify FrogBot to AI Gateway with the [app attribution](https://vercel.com/docs/ai-gateway/ecosystem/app-attribution) headers `http-referer: https://www.frogbot.ai` and `x-title: FrogBot`. To use your own values, set them in `headers`:

```ts
createGateway({
  providers: {
    vercel: { headers: { 'http-referer': 'https://example.com', 'x-title': 'Example' } }
  }
})
```

## Bedrock prompt caching

Bedrock Claude models translate Anthropic-style `cache_control` markers from `/v1/chat/completions` and `/v1/messages` into Bedrock `cachePoint` blocks. Markers are supported on system blocks, messages, and message content parts, including tool results. A request-level marker applies to the last message, caching the conversation prefix through that point.

The `5m` and `1h` TTL values pass through to Bedrock. Other TTL values are omitted without rejecting the request. This translation does not apply to Nova models, tool definitions, or `/v1/responses`.

---

## OpenAI prompt caching

OpenAI models translate Anthropic-style `cache_control` markers from `/v1/chat/completions` and `/v1/messages` into explicit OpenAI prompt cache breakpoints. Markers are supported on messages and message content parts. A request-level marker applies to the last message.

OpenAI retention accepts only `in_memory` and `24h`. Marker TTL values are omitted because OpenAI breakpoints have no TTL equivalent. TTL does not infer retention. This translation does not apply to Azure, custom OpenAI-compatible providers, tool definitions, or `/v1/responses`.

## OpenRouter

OpenRouter gives one API key access to models from many vendors. Set `OPENROUTER_API_KEY` in the server environment and configure `providers: { openrouter: {} }` in a standalone gateway, or `ai: { providers: { openrouter: true } }` in FrogBot. `OPENROUTER_BASE_URL` optionally overrides the API URL.

Model IDs keep OpenRouter's own `<creator>/<model>` form after the `openrouter/` prefix, including variants such as `:free`, for example `openrouter/anthropic/claude-sonnet-4.6` or `openrouter/google/gemma-4-31b-it:free`. FrogBot accepts the priced models that models.dev lists for OpenRouter. Dynamic routers without a fixed price, such as `openrouter/auto`, and models not yet in the catalog return a model-not-found error before any upstream call. Narrow the set with an allowlist, for example `models: ['anthropic/claude-sonnet-4.6']`; the allowlist applies only to config objects, not to a [pre-built instance](#pre-built-instances). Usage cost is estimated from those catalog prices, not read from OpenRouter's invoice.

Requests identify FrogBot to OpenRouter with the `X-OpenRouter-Title: FrogBot` and `HTTP-Referer: https://www.frogbot.ai` headers. Override them with `appName` and `appUrl`:

```ts
providers: {
  openrouter: { appName: 'Acme Support', appUrl: 'https://acme.example' }
}
```

Reasoning requests from every route become OpenRouter's `reasoning` option: `reasoning_effort` on `/v1/chat/completions`, `thinking` on `/v1/messages`, and `reasoning.effort` on `/v1/responses`. Disabled thinking is sent as effort `none`. Anthropic-style `cache_control` markers on messages and content parts reach OpenRouter unchanged.

On `/v1/chat/completions`, OpenRouter's own request fields pass through unchanged, for example `provider: { order: ['anthropic'], allow_fallbacks: false }`, `models` fallbacks, `plugins`, or a native `reasoning` object, which takes priority over `reasoning_effort`. `/v1/messages` and `/v1/responses` don't forward unknown request fields; use a [`beforeUpstream` hook](/gateway/hooks) to set `providerOptions.openrouter` there.

OpenRouter embeddings are not supported; `/v1/embeddings` with an `openrouter/...` model returns an error.

<Note>
  Prefer the built-in `openrouter` provider over a custom OpenAI-compatible entry pointing at `https://openrouter.ai/api/v1`. The generic entry drops per-part `cache_control`, cache-write token counts, OpenRouter's reasoning format, routing options, and PDFs supplied by URL.
</Note>

## Custom OpenAI-compatible endpoints

Any key that isn't a built-in provider name is a generic OpenAI-compatible endpoint. `baseURL` is required — it's what tells the gateway a key is a deliberate custom endpoint rather than a typo of a built-in name.

```ts
providers: {
  ollama: { baseURL: 'http://localhost:11434/v1' },
  'lm-studio': { baseURL: 'http://localhost:1234/v1' },
  vllm: {
    baseURL: 'https://vllm.internal.example/v1',
    apiKey: process.env.VLLM_API_KEY,
    headers: { 'x-deployment': 'production' }
  }
}
```

<Note>
  A key without `baseURL` fails validation at startup: `providers.ollama.baseURL must be a non-empty string`. This is the safety net for a mistyped built-in name (`openia` instead of `openai`) — it fails loudly instead of silently becoming an unreachable custom provider.
</Note>

Custom endpoint config accepts:

| Field | Required | Purpose |
| --- | --- | --- |
| `baseURL` | Yes | Base URL of the OpenAI-compatible API, typically ending in `/v1` |
| `apiKey` | No | Sent as `Authorization: Bearer <apiKey>` |
| `headers` | No | Extra request headers on every call |
| `queryParams` | No | Extra query params appended to every request URL |

Custom OpenAI-compatible providers keep their existing routing behavior and are not interpreted as built-in allowlists. In FrogBot's `ai.providers` surface, custom entries continue to use their required exhaustive model metadata. FrogBot router model strings also remain unchanged.

## Pre-built instances

Any provider key — built-in or custom — also accepts a pre-built AI SDK provider instance instead of a config object. Use this for a custom `fetch`, middleware, or anything the shorthand config can't express.

```ts
import { createOpenAI } from '@ai-sdk/openai'
import { createGateway } from '@frogbotai/gateway'

const customOpenAI = createOpenAI({
  fetch: myLoggingFetch
})

const gw = createGateway({
  providers: { openai: customOpenAI }
})
```

For a known key, the instance is checked against that provider's real AI SDK type. For a custom key, TypeScript can only confirm it looks like a provider (`languageModel` present) — the specific instance type isn't known ahead of time.

## Model IDs

Every route dispatches on a canonical `<provider>/<model>` ID. Built-in model IDs must exist in the configured catalog. Bedrock, Anthropic-on-Bedrock, and Azure additionally resolve friendly aliases to the exact ID the upstream API requires — for example `bedrock/claude-4-sonnet` resolves to `anthropic.claude-sonnet-4-20250514-v1:0` before catalog validation and the AI SDK sees it.
